Lesson 0001 · ForgePilot

讓佇列裡有第一件真的工作

目標很小：在 ForgePilot 自己的 repository 上跑到 WI-001 RUNNING，而且中途至少被擋一次。十分鐘。

你知道所有規則。這一課不重講名詞，只做一件事——把它接上去。MISSION 說得很直白：M1–M4 都通過了測試，但這個工具從來沒管過一件真實的工作，README 的流程是寫出來的不是用出來的。這一課把「寫出來的」變成「用出來的」前半段。

這一課結束時你會有

ForgePilot repo 裡一個真的 .forgepilot/state.json，裡面有一個 Goal、兩件有依賴關係的 Work Item，其中一件在 RUNNING。以及兩個只有真的動手才會撞到的擋點。

先看兩個會擋住你的東西

這是刻意先講的，因為它們會在第 1 步和第 4 步各擋你一次。知道會來，比撞上去再查快。

一，Story reference 必須在 specs/stories/ 底下。 這條寫死在 internal/repository/repository.go：路徑正規化與 symlink 解析之後仍須落在該目錄內，否則拒絕。而 ForgePilot 自己的 repo 沒有 這個目錄——它的規格住在 docs/specs/。所以拿它管自己，第一件事是建一個。

二，init 會改動工作樹。 它往 .gitignore 補上 .forgepilot/。而 verify 與 review 都要求工作樹嚴格乾淨——tracked 無修改、無 staged、無 untracked。所以 init 之後不 commit，之後每一步都會被拒絕。

STEP 1

建立 Story 目錄並寫下第一份 Story

ForgePilot 不讀 Story 的內容，也不猜它的 schema——它只確認那個路徑存在且在允許範圍內。所以這裡寫什麼都行，但既然是要管真實工作，就寫真的。

cd ~/Dev/CMG/ForgePilot
mkdir -p specs/stories
cat > specs/stories/DOGFOOD-001.md <<'EOF'
# 用 ForgePilot 管自己的下一段開發

把 README 寫出來的流程真的跑一次，記錄哪裡不順手。
EOF
STEP 2

init

go build -o /tmp/fp ./cmd/forgepilot
/tmp/fp init
Initialized ForgePilot in /Users/carl/Dev/CMG/ForgePilot

現在 git status 會顯示 .gitignore 被改了。先 commit 再往下，否則第 5 課的 verify 會拒絕你，而且錯誤訊息會指著這個檔案。

git add .gitignore specs/ && git commit -m "chore: dogfood ForgePilot on itself"
STEP 3

建一個 Goal

Goal 是需要跨多次工作推進的長期目標。--id 是你自己取的，不是系統配發的——只有 Work Item 的 ID 由受鎖操作發序號。

/tmp/fp goal create --id dogfood --title "用 ForgePilot 管自己的開發"
Goal dogfood created
STEP 4

加兩件有依賴的 Work Item

依賴用 Work Item ID，不用 Story 路徑。第二件依賴第一件，所以它一出生就是 PENDING。

/tmp/fp work add --goal dogfood --story specs/stories/DOGFOOD-001.md
/tmp/fp work add --goal dogfood --story specs/stories/DOGFOOD-002.md --depends-on WI-001

第二行會失敗——你還沒寫 DOGFOOD-002。這是第二個擋點，而且擋得對：Story reference 必須真的存在，否則 Work Item 會指向一份不存在的工程契約。補上檔案再跑一次。

WI-001 READY
Story: specs/stories/DOGFOOD-001.md
WI-002 PENDING
Story: specs/stories/DOGFOOD-002.md

READY 與 PENDING 是新增當下就決定的：全部依賴皆 DONE 則 READY，否則 PENDING。

STEP 5

問它下一件該做什麼，然後開始

next 是純查詢——它不 claim、不 start、不改任何狀態。它還會告訴你為什麼選中這一件。

/tmp/fp next
Next: WI-001
Goal: dogfood
Story: specs/stories/DOGFOOD-001.md
Verification: not verified
Reason: earliest READY work
/tmp/fp start WI-001
/tmp/fp status
WI-001 RUNNING

Goal dogfood ACTIVE: 用 ForgePilot 管自己的開發
  WI-001 RUNNING specs/stories/DOGFOOD-001.md
    not verified
    not reviewed
    Gates: 0 open
  WI-002 PENDING specs/stories/DOGFOOD-002.md
    not verified
    not reviewed
    Gates: 0 open
Next: none

Next: none 不是壞消息。WI-001 已經在跑（不再是 READY），WI-002 還卡在依賴上，所以沒有可以開始的工作——這正確。

注意 status 說了什麼

not verified 和 not reviewed 是刻意講出來的，不是留白。缺席的結果如果沉默，讀的人會把它當成沒問題的結果——這是 ADR-0008 一直在防的事。

檢查你記得的是規則，不是句子

這三題都不考定義，考的是「這個情況下會發生什麼」。你設計了這些規則，但知道規則和操作時想得起來是兩件事。

WI-001 正在 RUNNING，這時你在它上面開了一個 Gate。它的狀態變成什麼？

開關 Gate 不是 transition。阻擋是與狀態正交的另一個維度，所以狀態欄不動，只是這件工作推不動了。設 BLOCKED 或 WAITING_HUMAN 就會需要「記住進入阻擋前是什麼狀態」這種只為修補覆寫而存在的欄位（ADR-0007）。

你剛跑完 init，還沒 commit 那個被改動的 .gitignore，直接跑 verify WI-001。會怎樣？

拒絕，而且什麼都不寫——那是「無法驗證」，不是「驗證失敗」。乾淨採嚴格定義：tracked 無修改、無 staged、且無 untracked；init 產生的變動正好踩中。把 FAIL 記下來會是謊：沒有任何東西被驗證過。

WI-002 依賴 WI-001。WI-001 剛剛因為 approve 而進入 DONE。WI-002 什麼時候變成 READY？

完成與解鎖下游落在同一次受鎖的原子替換裡，所以 review approve 的輸出直接就印出 WI-002 READY。分成兩次交易，讀取者就會看到「A 已 DONE 但 B 仍 PENDING」的中間狀態（ADR-0001）。

接下來

你的佇列現在停在 RUNNING，這是刻意的——真正有意思的部分在後半段：verify 怎麼在隔離的 worktree 跑、Gate 怎麼在 approve 之後才顯出威力、以及為什麼你可能得 approve 兩次。那是第 2 課。

在那之前，先做一件事：把 DOGFOOD-001 這件工作真的做完——也就是實際去改點什麼、commit，然後帶著問題回來。第 2 課會用你自己的 commit 當驗證標的，不是 fixture。
