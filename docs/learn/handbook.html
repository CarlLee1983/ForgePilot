從 init 到 DONE 的完整操作

一份就跑得完的手冊：整條流程、每一個會擋住你的地方、status 每一行的意思，以及為什麼它要這樣擋。所有輸出都是實跑貼上來的。

這份文件取代原本的分課設計。你已經知道所有名詞與規則，它們定義在 CONTEXT.md、architecture.md 與 11 份 ADR，這裡不重講。這裡只回答一件事，手放在鍵盤上的時候該打什麼、會看到什麼、被擋住時該怎麼辦。

怎麼用這份文件

從頭到尾照著打一遍，大約二十分鐘。讀懂 status 與 它會拒絕你的地方 兩節可以單獨當參考查。最後有六題自我檢查，考的是「這個情況下會發生什麼」而不是定義。

本文所有輸出都來自 macOS 26.5.1 / Go 1.25.5 上以真實 binary 對真實 git repository 的實跑，只把 git 身分置換成 you@example.com。SHA 是那次實跑的真值，你自己跑會不同。

起手式：兩件會先絆倒你的事

先講，因為它們會在第一步和第三步各擋你一次，知道會來比撞上去再查快。

一，Story reference 必須落在 specs/stories/ 底下，而且檔案要真的存在。 這條寫死在 internal/repository/repository.go，路徑正規化與 symlink 解析之後仍須落在該目錄內。ForgePilot 自己的 repo 沒有 這個目錄（它的規格住在 docs/specs/），所以拿它管自己，第一個動作是建一個。ForgePilot 不讀 Story 的內容也不猜它的 schema，只確認那個路徑存在且在允許範圍內。

二，init 會弄髒工作樹。 它往 .gitignore 補上 .forgepilot/。不帶 flag 的 verify 與 COMMIT review 都要求嚴格乾淨，也就是 tracked 無修改、無 staged、無 untracked；走這條 commit-mode 路徑就先 commit。若要驗證尚未提交內容，改用 verify WI-001 --snapshot；後續 SNAPSHOT review 要求 workspace digest 未變。

受管理的專案還需要一個可執行的 make verify target。ForgePilot 不定義驗證的內容，只負責在乾淨且隔離的環境裡跑它、記下結果綁哪個 revision。

整條流程

STEP 1

init；commit mode 就立刻 commit

forgepilot init
git status --short
Initialized ForgePilot in /path/to/your/repo

?? .gitignore

那個 ?? 是 commit-mode 的擋點。若要走預設的 clean-HEAD verification，現在就處理掉：

git add .gitignore specs/ && git commit -m "chore: adopt forgepilot"

state 住在 .forgepilot/state.json，被程序鎖與原子替換保護，並綁定這個 repository 的身分，把目錄搬走它會拒絕讀，不會默默重綁到別的 repo。

STEP 2

宣告一個 Goal

Goal 的 --id 是你自己取的，不是系統配發的；只有 Work Item 的 ID 由受鎖操作發序號。

forgepilot goal create --id demo --title "示範 Goal"
Goal demo created
STEP 3

加兩件有依賴關係的 Work Item

依賴用 Work Item ID，不用 Story 路徑。READY 或 PENDING 在新增當下就決定，全部依賴皆 DONE 則 READY，否則 PENDING。

forgepilot work add --goal demo --story specs/stories/A-001.md
forgepilot work add --goal demo --story specs/stories/B-001.md --depends-on WI-001
WI-001 READY
Story: specs/stories/A-001.md
WI-002 PENDING
Story: specs/stories/B-001.md

兩種寫錯 Story 的方式各有各的訊息，兩者都在寫入之前就擋下來：

forgepilot: story reference "specs/stories/NOPE.md" does not exist
forgepilot: story reference must remain under specs/stories
STEP 4

問下一件該做什麼，然後開始

next 是純查詢，不 claim、不 start、不寫入任何東西，而且會說出它為什麼選中這一件。

forgepilot next
Next: WI-001
Goal: demo
Story: specs/stories/A-001.md
Verification: not verified
Reason: earliest READY work
forgepilot start WI-002
forgepilot start WI-001
forgepilot: work item "WI-002" is PENDING, not READY
WI-001 RUNNING

第一行是預期中的拒絕：WI-002 卡在依賴上。start 只接受 READY。

STEP 5

verify：在隔離的 worktree 跑 make verify

先看不帶 flag 的 commit mode 拒絕的樣子。工作樹髒的時候，它什麼都不寫。那是「無法驗證」，不是「驗證失敗」，記成 FAIL 會是謊。

echo scratch > dirty.txt
forgepilot verify WI-001
forgepilot: worktree is not clean; commit or stash the following before verifying:
?? dirty.txt

要走 commit mode 就清乾淨再跑；若要保留目前內容，直接改跑 forgepilot verify WI-001 --snapshot。commit mode 驗證在 detached worktree 裡執行，看不到主工作樹的未提交內容，Evidence 綁定完整的 commit SHA；snapshot mode 則先把那些內容固定成 immutable snapshot Candidate。

rm dirty.txt
forgepilot verify WI-001
EV-001 PASS at 9fda18ae576acbda2813b38a33fa2ebd28cade4c
WI-001 REVIEW

PASS 讓 RUNNING 進入 REVIEW，FAIL 退回 RUNNING。同一個 SHA 重跑不受限制；Evidence 只累積，不覆寫。驗證跑到一半被中斷（Ctrl-C、關終端機、關機）會被誠實記為 INTERRUPTED、工作退回 RUNNING，永遠不會寫成通過或失敗。

STEP 6

Gate：把「需要人決定」變成佇列擋得住的東西

遇到自己不該擅自決定的問題，開一個 Gate 而不是選一個繼續。Gate 不改狀態，阻擋是與狀態正交的另一個維度。

forgepilot gate open --work WI-001 \
  --question "要不要先把 Story B 拆小？" \
  --option "拆成兩件" --option "維持原樣" \
  --reason "B 的範圍看起來超過一次工作"
GATE-001 OPEN on WI-001
要不要先把 Story B 拆小？
Options: 拆成兩件 | 維持原樣

現在試著 approve。它會成功記下審查，但工作不會完成，而且最後一行明說少了什麼：

forgepilot review approve WI-001
EV-002 APPROVED at 9fda18ae576a
WI-001 REVIEW
Reviewed by: you@example.com (self-asserted; ForgePilot does not authenticate identities)
Not complete: 1 open gate(s)

整個工具最值得記住的一句話就是這個。approve 是一筆 Evidence，不是一個開關。審查發生了就該被記錄，完成與否是另外四項條件同時成立的結果。

forgepilot gate resolve GATE-001 --option "維持原樣" --note "B 還在可控範圍"
GATE-001 RESOLVED
Choice: 維持原樣
Decided by: you@example.com (self-asserted; ForgePilot does not authenticate identities)

被取消的 Gate 也會留在 status 裡。一個沒人看得到的取消，等於繞過待決事項的暗門。

STEP 7

reject：退回去，理由留在檔案裡

forgepilot review reject WI-001 --reason "commit message 沒有交代 why"
EV-003 REJECTED at 9fda18ae576a
WI-001 RUNNING
Reviewed by: you@example.com (self-asserted; ForgePilot does not authenticate identities)

REJECTED 讓工作退回 RUNNING。那筆 PASS 沒有消失，它與 REJECTED 並排留著，因為「驗證通過但人不接受」跟「驗證沒過」是兩件不同的事，記錄不該把它們混成一件。

STEP 8

改完重跑，然後真的完成

git commit -am "docs: explain why"
forgepilot verify WI-001
forgepilot review approve WI-001 --pr "CarlLee1983/ForgePilot#12" --note "看過 diff 與 evidence"
EV-004 PASS at 26be05c984479e08f91de576a84c2635ebee30aa
WI-001 REVIEW

EV-005 APPROVED at 26be05c98447
WI-001 DONE
Reviewed by: you@example.com (self-asserted; ForgePilot does not authenticate identities)
WI-002 READY

完成與解鎖下游在同一次受鎖交易裡發生，所以 WI-002 READY 直接印在 approve 的輸出上，不必再跑一次任何指令。分成兩次交易，別的 process 就會讀到「A 已 DONE 但 B 仍 PENDING」的中間狀態。

--pr 是選填的。帶了就記進那筆 Evidence，之後 status 會顯示；沒帶就什麼都不印，也不會有任何提示。缺 PR 是合法狀態，不是待辦事項。DONE 是終態，沒有 reopen；需要再動就開一件新的 Work Item。

STEP 9

stale：COMMIT candidate 的 HEAD 動了，舊的 PASS 就不算數

這是最容易讓人愣住的一段。WI-002 驗證通過後，你又 commit 了一次，然後 approve：

  WI-002 REVIEW specs/stories/B-001.md
    EV-006 PASS at 26be05c98447 (stale; HEAD is now 96f3e0b2eef1)
forgepilot review approve WI-002
EV-007 APPROVED at 96f3e0b2eef1
WI-002 REVIEW
Reviewed by: you@example.com (self-asserted; ForgePilot does not authenticate identities)
Not complete: the latest PASS is at revision 26be05c98447 but the approval is at 96f3e0b2eef1

審查記下來了，工作沒完成，原因寫在最後一行。你審的是新的 HEAD，通過驗證的是舊的那個 commit。重新 verify 一次，讓兩者對齊，再 approve：

forgepilot verify WI-002
forgepilot review approve WI-002 --note "收尾"
EV-009 PASS at 96f3e0b2eef1f08b68659ee7fb468b11792a353d
WI-002 REVIEW

EV-010 APPROVED at 96f3e0b2eef1
WI-002 DONE
STEP 10

Goal 的生命週期

Goal 被 block 之後，底下的工作連 verify 都不行。這是刻意的，暫停就該是真的暫停。

forgepilot goal block demo --reason "等使用者確認範圍"
forgepilot verify WI-002
forgepilot goal unblock demo
Goal demo BLOCKED
forgepilot: work item "WI-002" does not belong to an active goal
Goal demo ACTIVE

還有工作沒完成時，Goal 不准被宣告完成，而且它會指名是哪一件卡著：

forgepilot: goal "demo" still has unfinished work: WI-002 is REVIEW

全部 DONE 之後才過得去：

forgepilot goal complete demo
Goal demo COMPLETED

讀懂 status 的每一行

status 是唯一一個把所有東西攤開的指令，它的每一行都有測試在盯著。下面是一份完成後的完整輸出。

Goal demo COMPLETED: 示範 Goal
  WI-001 DONE specs/stories/A-001.md
    EV-004 PASS at 26be05c98447
    EV-005 APPROVED at 26be05c98447 by you@example.com (self-asserted) on CarlLee1983/ForgePilot#12: 看過 diff 與 evidence
    Gates: 0 open
      GATE-001 RESOLVED 要不要先把 Story B 拆小？ -> 維持原樣 (self-asserted by you@example.com)
  WI-002 DONE specs/stories/B-001.md
    EV-009 PASS at 96f3e0b2eef1
    EV-010 APPROVED at 96f3e0b2eef1 by you@example.com (self-asserted): 收尾
    Gates: 0 open
Next: none
你看到的它在說什麼
not verified / not reviewed刻意講出來的缺席，不是留白。沉默的缺席會被讀成沒問題的結果。
EV-004 PASS at 26be05c98447最新一筆驗證結果與它綁定的 revision。Evidence 只累積不覆寫，編號連續。
(stale; HEAD is now …)這筆 PASS 驗的不是現在的 HEAD。它不觸發任何 transition，只是誠實標示。
Not complete: …審查已記錄但工作沒完成，這行說出還差什麼。這是最該讀的一行。
Gates: N open擋住這件工作的 Gate 數。底下逐條列出所有開過的 Gate，含已解決與已取消的。
(self-asserted)身分來自 git config user.email 或 --by，沒有任何認證。這五個字是刻意印出來的，免得誰把它當成經過驗證的簽章。
Next: none沒有可以開始的工作，不是壞消息，正在跑的不是 READY，卡依賴的也不是。

純讀指令（status、next）不寫入 state，驗證進行中也照樣能跑。同一件工作不能並行驗證，不同工作可以。

它會拒絕你的地方

整理成一張表，全部是實跑貼上來的訊息。被擋住的時候直接搜這裡。

訊息怎麼辦
no .forgepilot state found; run forgepilot init first還沒 init，或不在那個 repo 裡。help 不需要 state 就能跑。
story reference "…" does not exist先把 Story 檔案寫出來。Work Item 不該指向不存在的工程契約。
story reference must remain under specs/stories路徑正規化與 symlink 解析後仍須落在該目錄內。
work item "WI-002" is PENDING, not READY依賴還沒全部 DONE。start 只接受 READY。
worktree is not clean; commit or stash the following before verifying:這是不帶 flag 的 commit mode；訊息會列出髒的檔案。乾淨採嚴格定義，untracked 也算。不寫任何 Evidence；若要驗證當前內容，改用 verify <work-id> --snapshot。
this revision has no makefile, so `make verify` cannot be run受管理的專案得自己提供 canonical verification。同樣不留 Evidence。
work item "WI-002" does not belong to an active goalGoal 是 BLOCKED 或已結束。先 goal unblock。
goal "demo" still has unfinished work: WI-002 is REVIEWGoal 完成的宣告要有實質意義，它會指名卡住的那一件。
cannot unblock goal "demo": it is ACTIVE沒被 block 就不能解除。狀態轉移不接受無意義的操作。
no git user.email is configured; pass --by to state who is deciding錯誤訊息直接告訴你哪個 flag 能修好它。
--reason is requiredgoal block、review reject、gate cancel 都要理由。理由留在檔案裡，不留在你腦裡。

migrate 只在換過 binary 之後才需要。已經是最新的時候它會這樣說，而且成功結束。

State is already at schema version 4; nothing to migrate.

舊版 state 不會被自動升級，migrate 先備份成 state.json.vN.bak 再升，備份檔已存在時拒絕執行。重複執行是安全的。

四項條件，缺一不可

一件 Work Item 進入 DONE，需要以下四項同時成立。status 的 Not complete: 那行永遠在說缺的是哪一項。

條件不成立時會怎樣
有一筆 APPROVED 的 Human Review停在 REVIEW。沒有任何指令能繞過人。
最新一筆 PASS 的 revision 等於審查當下的 HEAD審查被記錄，工作不完成，訊息並列兩個 SHA。
沒有 open 的 Gate審查被記錄，工作不完成，訊息報開著的 Gate 數。
Goal 是 ACTIVE連 verify 都不給跑。

PR reference 不在這四項裡。它是描述而非門檻，帶了就記、沒帶就沉默。

自我檢查

六題都不考定義，考的是「這個情況下會發生什麼」。知道規則和操作時想得起來是兩件事。

WI-001 正在 RUNNING，這時你在它上面開了一個 Gate。它的狀態變成什麼？

開關 Gate 不是 transition。阻擋是與狀態正交的另一個維度，所以狀態欄不動，只是這件工作推不動了。設 BLOCKED 或 WAITING_HUMAN 就會需要「記住進入阻擋前是什麼狀態」這種只為修補覆寫而存在的欄位（ADR-0007）。

你剛跑完 init，還沒 commit 那個被改動的 .gitignore，直接跑 verify WI-001。會怎樣？

拒絕，而且什麼都不寫。那是「無法驗證」，不是「驗證失敗」。乾淨的定義很嚴格，tracked 無修改、無 staged、且無 untracked。把 FAIL 記下來會是謊，因為沒有任何東西被驗證過。

WI-002 依賴 WI-001。WI-001 剛剛因為 approve 而進入 DONE。WI-002 什麼時候變成 READY？

完成與解鎖下游落在同一次受鎖的原子替換裡，所以 review approve 直接印出 WI-002 READY。分成兩次交易，讀取者就會看到「A 已 DONE 但 B 仍 PENDING」的中間狀態（ADR-0001）。

工作有一筆 PASS，但那之後你又 commit 了一次。現在 approve，會發生什麼？

審查真的發生了就該被記錄，APPROVED 是一筆 Evidence，不是開關。但完成需要「最新 PASS 的 revision 等於審查當下的 HEAD」，所以 Not complete: 那行會把兩個 SHA 並列給你看。修法是重跑一次 verify 讓兩者對齊。

你 reject 了一件工作。它那筆已經存在的 PASS Evidence 會怎樣？

Evidence 只累積不覆寫。「驗證通過但人不接受」與「驗證沒過」是兩件不同的事，把它們混成一件會讓之後讀記錄的人分不出來。工作退回 RUNNING，記錄一筆都不少。

approve 時不帶 --pr，status 之後會怎麼顯示那筆審查？

缺 PR 是合法狀態，不是待辦事項。PR reference 是描述而非完成條件，所以沒有就沉默。而 status「不對未完成的原因沉默」的要求只涵蓋真正的完成條件，PR 不在其中。

還沒被解決的摩擦

真的拿它管過一段工作之後累積下來的不順手，記在 learning-records，是未來版本的輸入而不是待辦清單。目前有兩項。Story 目錄的硬性要求讓一個規格不放在 specs/stories/ 的專案（包括 ForgePilot 自己）第一步就得建空目錄；init 弄髒工作樹會讓新使用者第一次不帶 flag 的 verify 失敗，而錯誤訊息指著 init 自己造成的檔案。要驗證尚未提交內容可改用 verify --snapshot。

用起來還有哪裡卡，就再記一筆。這是這個工具目前唯一的真實回饋來源。
