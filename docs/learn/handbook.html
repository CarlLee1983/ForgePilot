從 init 到 DONE 的完整操作

一份就跑得完的手冊：整條流程、每一個會擋住你的地方、status 每一行的意思，以及為什麼它要這樣擋。所有輸出都是實跑貼上來的。

這份文件取代原本的分課設計。你已經知道所有名詞與規則，它們定義在 CONTEXT.md、architecture.md 與 ADR，這裡不重講。這裡只回答一件事，手放在鍵盤上的時候該打什麼、會看到什麼、被擋住時該怎麼辦。

怎麼用這份文件

ForgePilot 不跑迴圈，迴圈是你（或你的 coding Agent）在跑：問 next、做它說的事、再問一次。從頭到尾照著打一遍，大約二十分鐘。讀懂 status 與 它會拒絕你的地方 兩節可以單獨當參考查。最後有六題自我檢查，考的是「這個情況下會發生什麼」而不是定義。

本文所有輸出都來自 macOS 上以真實 binary 對真實 git repository 的實跑，只把 git 身分置換成 you@example.com、repository 路徑換成 /path/to/your/repo。SHA 是那次實跑的真值，你自己跑會不同；log 檔名只完整列出第一個，其餘以 … 省略時間戳與隨機尾碼。

起手式：兩件會先絆倒你的事

先講，因為它們會擋你，知道會來比撞上去再查快。

一，Story reference 必須落在 specs/stories/ 底下，而且路徑要真的存在。 這條由 internal/repository 檢查，路徑正規化與 symlink 解析之後仍須落在該目錄內，goal import 在寫入之前就會擋下來。ForgePilot 不讀 Story 的內容也不猜它的 schema，只確認那個路徑存在且在允許範圍內。

二，init 會弄髒工作樹。 它往 .gitignore 補上 .forgepilot/。不帶 flag 的 verify 要求嚴格乾淨，也就是 tracked 無修改、無 staged、無 untracked；走這條 commit-mode 路徑就先 commit。要驗證尚未提交的內容，改用 verify <work-id> --snapshot。

受管理的專案還需要一個可執行的 make verify target，而且它必須能在全新 checkout 上通過，因為 ForgePilot 在隔離的 detached worktree 跑它。ForgePilot 不定義驗證的內容，也不管 toolchain 版本，只負責在乾淨且隔離的環境裡跑它、記下結果綁哪個 Candidate。

整條流程

STEP 1

init，然後 commit

forgepilot init
git status --short
Initialized ForgePilot in /path/to/your/repo
?? .gitignore

那個 ?? 是 commit-mode 的擋點，現在就處理掉：

git add .gitignore && git commit -m "chore: ignore ForgePilot state"

state 住在 .forgepilot/state.json，被程序鎖與原子替換保護。

STEP 2

用一份 Goal Plan 匯入整張 DAG

Goal 與所有節點由一份 JSON 一次建立；沒有 work add。節點 id 就是 Work Item ID，之後 start、verify 都用它，節點順序是多件工作同時 READY 時 next 的推薦順序。拆單拆得對不對是你與上游的責任，ForgePilot 只保證收到的是合法 DAG、Story 路徑存在。

{
  "goal": { "id": "billing-sync", "title": "Billing sync", "require_approval": false },
  "nodes": [
    { "id": "schema",   "story": "specs/stories/schema",   "depends_on": [] },
    { "id": "sync-job", "story": "specs/stories/sync-job", "depends_on": ["schema"] },
    { "id": "docs",     "story": "specs/stories/docs",     "depends_on": [] }
  ]
}
forgepilot goal import plans/billing-sync.json
Goal billing-sync imported: 3 nodes
  schema READY specs/stories/schema
  sync-job PENDING specs/stories/sync-job
  docs READY specs/stories/docs

計畫有任何一處錯，整份都不寫入，錯誤訊息指出節點與欄位：

forgepilot: node "a": story: story reference must be located under specs/stories: "specs/stories/NOPE"
forgepilot: node "a": depends_on forms a cycle: a -> b -> a

補單時改計畫檔再匯入同一個 Goal：只能新增節點，既有節點必須全數列出且內容不變；成功輸出 Goal … updated: added N nodes，完全相同則是 unchanged。DONE 是終態，要重做就新增一個節點，讓「為什麼重做」有地方被記錄。

STEP 3

問下一件該做什麼，然後開始

next 是純查詢，不 start、不寫入任何東西，只給一個動作，並說出為什麼選中它。

forgepilot next
Next: schema
State: READY
Goal: billing-sync
Story: specs/stories/schema
Action: forgepilot start schema
Reason: earliest READY work

給 Agent 的迴圈用 next --json：每個欄位永遠存在，沒有值就是空字串，waiting 是空陣列。接著試兩個預期中的拒絕：

forgepilot start sync-job
forgepilot start schema
forgepilot start docs
forgepilot: work item "sync-job" is PENDING: dependencies not DONE: schema
schema RUNNING
forgepilot: work item "docs" cannot proceed: work item "schema" is RUNNING; only one work item can be RUNNING or VERIFYING at a time

第一個拒絕是依賴；第三個是單一佔位：同一 workspace 同時最多一件 RUNNING 或 VERIFYING，錯誤指出佔位的是誰。docs 明明也是 READY，卻要等 schema 做完。

STEP 4

Gate：把「需要人決定」變成帳本擋得住的東西

遇到自己不該擅自決定的問題，開一個 Gate 而不是選一個繼續。Gate 不改狀態，阻擋是與狀態正交的另一個維度。

forgepilot gate open --work schema \
  --question "要不要先把 schema 拆小？" \
  --option "拆成兩件" --option "維持原樣" \
  --reason "範圍看起來超過一次工作"
GATE-001 OPEN on schema
要不要先把 schema 拆小？
Options: 拆成兩件 | 維持原樣

現在 verify 被擋，而且 next 明說在等人，這是換 session 的 Agent 得知「別動它」的方式：

forgepilot: work item "schema" is blocked by open gate(s) GATE-001; resolve or cancel them first

No agent-actionable work.

Waiting: schema
Reason: unresolved Gate GATE-001
forgepilot gate resolve GATE-001 --option "維持原樣" --note "還在可控範圍"
GATE-001 RESOLVED
Choice: 維持原樣
Decided by: you@example.com (self-asserted; ForgePilot does not authenticate identities)

被取消的 Gate 也會留在 status 裡。一個沒人看得到的取消，等於繞過待決事項的暗門。

STEP 5

verify：在隔離的 worktree 對確切的 Candidate 跑 make verify

先看工作樹髒的時候。不帶 flag 的 commit mode 拒絕，而且什麼都不寫：那是「無法驗證」，不是「驗證失敗」，記成 FAIL 會是謊。

touch fail.flag
forgepilot verify schema
forgepilot: worktree is not clean; commit or stash the following before verifying:
?? fail.flag

改用 --snapshot：用 private Git index 把工作樹固定成 immutable snapshot Candidate，不動你的 branch、HEAD、index 與檔案，也不需要 WIP commit。這個示範專案的 make verify 在 fail.flag 存在時失敗：

forgepilot verify schema --snapshot
Candidate: SNAPSHOT
Revision: 387a3db9aa84b61bdb35572327961b3277629814
Base: c06edae6bff8569ec12497e5eff409175fd009dc
Log: /path/to/your/repo/.forgepilot/logs/VR-001-387a3db9aa84-20261002T111154.971283000Z-c241eabe350e545a.log
EV-001 FAIL at 387a3db9aa84b61bdb35572327961b3277629814
schema RUNNING

FAIL 讓工作留在 RUNNING，next 轉為 REPAIR，status --work 的 Completion 寫著原因：

Next: schema
State: RUNNING
Goal: billing-sync
Story: specs/stories/schema
Action: repair implementation and verify again
Reason: latest verification failed

schema RUNNING
Goal: billing-sync ACTIVE
Approval required: no
Story: specs/stories/schema
Verification: EV-001 FAIL at 387a3db9aa84 (snapshot)
Review: not required
Blocking gates: none
Completion: verification failed

讀 Log: 指的檔案、修好（這裡是 rm fail.flag）再 verify。PASS 的那一刻，工作直接是 DONE，下游同一次交易解鎖：

Candidate: SNAPSHOT
Revision: ebb442a6660aad42a643362bee868e45a792ddd6
Base: c06edae6bff8569ec12497e5eff409175fd009dc
Log: /path/to/your/repo/.forgepilot/logs/VR-002-ebb442a6660a-….log
EV-002 PASS at ebb442a6660aad42a643362bee868e45a792ddd6
schema DONE
sync-job READY

驗證跑到一半被中斷（Ctrl-C、關終端機、關機）會被誠實記為 INTERRUPTED、工作退回 RUNNING，永遠不會寫成通過或失敗；next 在下一次 verify 回收它之前會給 RECOVER。Evidence 只累積，不覆寫。

STEP 6

收尾：最後一件 DONE，Goal 自動完成

commit mode 在已提交的 HEAD 上驗證，Evidence 綁定完整的 commit SHA。沒有「完成指令」：sync-job 與 docs 都是 start、實作、verify，PASS 就 DONE。

forgepilot start sync-job
forgepilot verify sync-job
forgepilot start docs
forgepilot verify docs
sync-job RUNNING
Log: /path/to/your/repo/.forgepilot/logs/VR-003-c06edae6bff8-….log
EV-003 PASS at c06edae6bff8569ec12497e5eff409175fd009dc
sync-job DONE
docs RUNNING
Log: /path/to/your/repo/.forgepilot/logs/VR-004-c06edae6bff8-….log
EV-004 PASS at c06edae6bff8569ec12497e5eff409175fd009dc
docs DONE
Goal billing-sync COMPLETED

完成與解鎖下游（以及 Goal 完成）在同一次受鎖交易裡發生，所以 sync-job READY 直接印在 schema 的 verify 輸出上，不必再跑任何指令。分成兩次交易，別的 process 就會讀到「A 已 DONE 但 B 仍 PENDING」的中間狀態。next 此時回 Goal billing-sync is completed: every Work Item is DONE.；DONE 是終態，沒有 reopen。

STEP 7

選用：要求 Approval 的 Goal

有些 Goal 要人逐件審。在計畫中宣告 "require_approval": true（匯入時定下，之後不能改），PASS 就先進 REVIEW，不是 DONE：

$ forgepilot goal import plans/audit.json
Goal audit imported: 1 nodes
  audit-log READY specs/stories/audit-log
$ forgepilot start audit-log
audit-log RUNNING
$ forgepilot verify audit-log
Log: /path/to/your/repo/.forgepilot/logs/VR-005-c06edae6bff8-….log
EV-005 PASS at c06edae6bff8569ec12497e5eff409175fd009dc
audit-log REVIEW
$ forgepilot next
No agent-actionable work.

Waiting: audit-log
Reason: human review required

REVIEW 不佔位，人在決定的時候沒有任何東西在執行。人可以退回，理由留在檔案裡：

forgepilot review reject audit-log --reason "沒有處理錯誤路徑"
EV-006 REJECTED at c06edae6bff8
audit-log RUNNING
Reviewed by: you@example.com (self-asserted; ForgePilot does not authenticate identities)

REJECTED 讓工作退回 RUNNING，那筆 PASS 沒有消失，與 REJECTED 並排留著，因為「驗證通過但人不接受」跟「驗證沒過」是兩件不同的事。改完重新 verify 回到 REVIEW，再 approve：

forgepilot review approve audit-log --note "看過 diff 與 evidence"
EV-008 APPROVED at fe7b5ef1f3a0
audit-log DONE
Reviewed by: you@example.com (self-asserted; ForgePilot does not authenticate identities)
Goal audit COMPLETED

對不要求 Approval 的 Goal 執行 review 一律拒絕：goal "g" does not require approval: its work completes when verification passes, so there is nothing to review。

STEP 8

stale：REVIEW 期間 HEAD 動了，舊的 PASS 就不算數

stale 只對 REVIEW 工作有意義。audit-log 驗證通過後你又 commit 了一次，然後 approve：

forgepilot: review approve audit-log: work item "audit-log" has a stale verified candidate: its PASS EV-005 no longer names the current candidate; run forgepilot verify audit-log

audit-log REVIEW
Goal: audit ACTIVE
Approval required: yes
Story: specs/stories/audit-log
Verification: EV-005 PASS at c06edae6bff8 (stale)
Review: not reviewed
Blocking gates: none
Completion: verification stale
Cannot advance: waiting for review approve

Next: audit-log
State: REVIEW
Goal: audit
Story: specs/stories/audit-log
Action: forgepilot verify audit-log
Reason: verified candidate is stale

approve 被拒、不留紀錄，next 直接給出該跑的指令。你審的是新的 HEAD，通過驗證的是舊的那個 commit，重新 verify 一次讓兩者對齊。DONE 的工作則不判 stale：它已經完成，後續 commit 不會讓它重開。

STEP 9

放棄整個 Goal

forgepilot goal cancel billing-sync --reason "需求取消"
Goal billing-sync CANCELLED

被取消的 Goal 的工作不再被 next 推薦；沒有其他 ACTIVE Goal 時，next 回 Goal billing-sync is cancelled (需求取消). No actionable work.。底下未完成的工作不能 start，status 說明 goal billing-sync is CANCELLED，也不能再匯入。進行中的驗證跑完仍會記錄 Evidence。

讀懂 status 的每一行

status 是唯一一個把所有東西攤開的指令，它的每一行都有測試在盯著。下面是 STEP 1 到 STEP 7 跑完之後的完整輸出。

Goal billing-sync COMPLETED: Billing sync
  Approval required: no
  schema DONE specs/stories/schema
    EV-002 PASS snapshot ebb442a6660a
    Gates: 0 open
      GATE-001 RESOLVED 要不要先把 schema 拆小？ -> 維持原樣 (self-asserted by you@example.com)
  sync-job DONE specs/stories/sync-job
    EV-003 PASS at c06edae6bff8
    Gates: 0 open
  docs DONE specs/stories/docs
    EV-004 PASS at c06edae6bff8
    Gates: 0 open
Goal audit COMPLETED: Audit trail
  Approval required: yes
  audit-log DONE specs/stories/audit-log
    EV-007 PASS at fe7b5ef1f3a0
    EV-008 APPROVED at fe7b5ef1f3a0 by you@example.com (self-asserted): 看過 diff 與 evidence
    Gates: 0 open
Next: none

還有工作沒完成時，每件工作底下會多一行 Cannot advance:，這是最該讀的一行，例如 depends on schema, which is RUNNING、open Gate GATE-001、waiting for review approve、goal g is CANCELLED。

你看到的它在說什麼
PENDING / READY讀取時依「依賴是否全部 DONE」算出來的，不保存。READY 不表示可以忽略該工作自己的 Gate。
not verified / not reviewed刻意講出來的缺席，不是留白。沉默的缺席會被讀成沒問題的結果。
EV-004 PASS at c06edae6bff8最新一筆驗證結果與它綁定的 revision；snapshot Candidate 顯示為 PASS snapshot …。Evidence 只累積不覆寫，編號連續。
(stale)status --work 的寫法；完整 status 會多說原因：(stale; HEAD is now …) 或 (stale; workspace no longer matches verified snapshot)。REVIEW 工作的這筆 PASS 驗的不是現在的 Candidate。它不觸發任何 transition，只是誠實標示，並讓 next 建議重新驗證。
Cannot advance: …這件工作為什麼不能往前，是依賴、Gate、等待 approval、佔位、驗證進行中，還是 Goal 已結束。
Gates: N open擋住這件工作的 Gate 數。底下逐條列出所有開過的 Gate，含已解決與已取消的。
(self-asserted)身分來自 git config user.email 或 --by，沒有任何認證。這幾個字是刻意印出來的，免得誰把它當成經過驗證的簽章。
Next: none沒有可以開始的工作，不是壞消息，正在跑的不是 READY，卡依賴的也不是。

純讀指令（status、next）不寫入 state，驗證進行中也照樣能跑。

它會拒絕你的地方

整理成一張表，全部是實跑貼上來的訊息。被擋住的時候直接搜這裡。

訊息怎麼辦
no .forgepilot state found; run forgepilot init first還沒 init，或不在那個 repo 裡。
story reference must be located under specs/stories: "…"Story 路徑不存在、不在 specs/stories/ 底下，或逃出 repository。整份計畫不寫入。
depends_on forms a cycle: a -> b -> a計畫不是合法 DAG。改計畫檔再匯入。
work item "sync-job" is PENDING: dependencies not DONE: schema依賴還沒全部 DONE。start 只接受 READY。
… only one work item can be RUNNING or VERIFYING at a time已有一件佔位。訊息指出是哪一件，先處理它，不要繞過。
work item "schema" is blocked by open gate(s) GATE-001; …有未解除的 Gate，start 與 verify 都擋。等人 gate resolve，或問錯了就 gate cancel。
worktree is not clean; commit or stash the following before verifying:不帶 flag 的 commit mode；訊息會列出髒的檔案。乾淨採嚴格定義，untracked 也算。不寫任何 Evidence；要驗證當前內容，改用 verify <work-id> --snapshot。
work item "a" is DONE; only RUNNING or REVIEW work can be verifiedDONE 是終態，不能再驗證，也沒有 reopen。
goal "g" does not require approval: …對不要求 Approval 的 Goal 呼叫了 review。
… has a stale verified candidate: …; run forgepilot verify …REVIEW 之後 Candidate 變了。照訊息重新 verify。
goal "g" is CANCELLED; a plan can only be imported into an ACTIVE goal終態 Goal 不能再匯入。新開一個 Goal。
unknown command "work"已移除的指令（work add、migrate、reconcile 等）。現行指令見 forgepilot --help。
no git user.email is configured; pass --by to state who is deciding錯誤訊息直接告訴你哪個 flag 能修好它。

舊版（schema 19 之前）寫下的 state 會被拒讀，沒有升級指令。訊息建議以 Goal Plan 重新匯入：為每個未完成的 Goal 寫一份 Goal Plan，把舊的 .forgepilot/ 封存後 init、再逐份 goal import。

DONE 的條件

一件 Work Item 進入 DONE 的條件很短，status 的 Cannot advance: 與 Completion: 永遠在說缺的是哪一項。

Goal條件
預設（不要求 Approval）verify 在目前 Candidate 上 PASS，無未解除 Gate，Goal 為 ACTIVE。三者同一次交易內成立就 DONE。
require_approvalPASS 先進 REVIEW；review approve 在記錄的同一次交易內再檢查：最新 PASS 仍是目前 Candidate、無未解除 Gate、Goal 為 ACTIVE。

沒有任何指令可以繞過這些條件：沒有 done、沒有 complete，也沒有測試專用的 approve。全部節點 DONE 時 Goal 自動 COMPLETED。

自我檢查

六題都不考定義，考的是「這個情況下會發生什麼」。知道規則和操作時想得起來是兩件事。

schema 正在 RUNNING，這時你在它上面開了一個 Gate。它的狀態變成什麼？

開關 Gate 不是 transition。阻擋是與狀態正交的另一個維度，所以狀態欄不動，只是這件工作推不動了。設 BLOCKED 或 WAITING_HUMAN 就會需要「記住進入阻擋前是什麼狀態」這種只為修補覆寫而存在的欄位（ADR-0007）。

你剛跑完 init，還沒 commit 那個被改動的 .gitignore，直接跑 verify schema。會怎樣？

拒絕，而且什麼都不寫。那是「無法驗證」，不是「驗證失敗」。乾淨的定義很嚴格，tracked 無修改、無 staged、且無 untracked。把 FAIL 記下來會是謊，因為沒有任何東西被驗證過。要驗證當前工作樹請用 --snapshot。

sync-job 依賴 schema，Goal 不要求 Approval。schema 的 verify PASS 之後，sync-job 什麼時候變成 READY？

PASS 即 DONE，完成與解鎖下游落在同一次受鎖的原子替換裡，所以 verify 直接印出 schema DONE 與 sync-job READY。READY 本來就不保存：它在每次讀取時由「依賴是否全部 DONE」算出來，沒有 refresh，也沒有 reconcile。分成兩次交易，讀取者就會看到「A 已 DONE 但 B 仍 PENDING」的中間狀態（ADR-0001）。

schema 正在 RUNNING，docs 也是 READY。你對 docs 執行 start，會發生什麼？

同一 workspace 同時最多一件 RUNNING 或 VERIFYING（單一佔位）。READY 只表示依賴滿足，不表示輪得到它；next 在有佔位時也不會推薦開始其他工作。平行分支執行延後到確實需要時另行設計（ADR-0040）。

在要求 Approval 的 Goal 裡，你 reject 了一件工作。它那筆已經存在的 PASS Evidence 會怎樣？

Evidence 只累積不覆寫。「驗證通過但人不接受」與「驗證沒過」是兩件不同的事，把它們混成一件會讓之後讀記錄的人分不出來。工作退回 RUNNING，記錄一筆都不少。

工作已經 DONE，之後你又 commit 了新的變更。status 會把它標成 stale 並要求重新驗證嗎？

stale 只對 REVIEW 工作有意義，用途是提示需要重驗。對終態工作那個提示是錯的，沒有行動意義的警示會讓人開始忽略所有警示。要重做就在計畫檔新增一個節點，讓「為什麼重做」有地方被記錄（ADR-0006）。

還沒被解決的摩擦

真的拿它管過一段工作之後累積下來的不順手，記在 learning-records，是未來版本的輸入而不是待辦清單。目前有兩項。Story 目錄的硬性要求讓一個規格不放在 specs/stories/ 的專案第一步就得建目錄；init 弄髒工作樹會讓新使用者第一次不帶 flag 的 verify 失敗，而錯誤訊息指著 init 自己造成的檔案。要驗證尚未提交內容可改用 verify --snapshot。

用起來還有哪裡卡，就再記一筆。這是這個工具目前唯一的真實回饋來源。
