# verify 先回收孤兒，再判斷能不能開始新的一次執行

`forgepilot verify` 做兩件事：把上一次被中斷、無人收尾的 Verification Run 記為 INTERRUPTED，以及開始新的一次執行。這兩件事現在分開判斷——回收無條件發生，開始新執行則受 Gate、Goal 狀態、工作樹乾淨與否等全部條件約束。

M2 當初把兩者綁在一起，並在 `internal/cli/verify.go` 明文承諾「指令失敗就代表什麼都沒改，包括沒有偷偷回收孤兒」。M3 引入 Gate 之後那個綁定開始傷人：一件工作在驗證中途被中斷，之後有人在它上面開了 Gate，於是 `verify` 被拒絕、孤兒無法被回收、工作永遠停在 VERIFYING，而 `status` 還叫使用者去跑那個當下必定被拒絕的 `verify`。產品的指示照做會失敗。

決定以「記錄已發生的事」與「開始新工作」的分界為準——那條線本來就寫在 M3 的定案裡（Goal 非 ACTIVE 擋的是後者，不是前者）。中斷是已經發生的事實，它的 Evidence 不該被任何阻擋條件扣住；能不能再跑一次，才是阻擋條件要回答的問題。

M2 的承諾因此被縮小而非取消：**沒有孤兒可回收時，被拒絕的 `verify` 仍然什麼都不寫**。有孤兒時它只寫那一筆 INTERRUPTED，不會標記新的執行、不會建立 worktree，而且回收一定印在輸出上——M2 真正在意的是「偷偷」，不是「寫入」。

**Consequences:** `verify` 失敗時可能已經改變了 state，因此錯誤訊息與輸出必須同時出現，讓使用者看得到發生了什麼。回收與開始新執行從單一交易變成兩次交易，中間的狀態是「舊執行已收尾、工作回到 RUNNING」——那是一個完整而正確的狀態，不是缺口。

**Falsified if:** `internal/cli/verify.go` 出現任何在回收孤兒之前就會拒絕整個指令的條件，或 `internal/work/evidence.go` 的 `ReclaimRun` 開始詢問 Gate 或 Goal 的狀態。那表示這個分界被取消，工作會再次卡在 VERIFYING 且無路可出。
