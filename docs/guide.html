ForgePilot 最簡單的講法 完成條件 跟 agent 一起用 怎麼用 手冊 GitHub

Passive DAG Ledger

讓「做完了」這句話變貴

ForgePilot 不寫程式，不啟動也不取代你的 coding agent。證據不夠的時候，它不讓任何人宣告工作完成，包括 agent，也包括你自己。

01

用五歲小孩聽得懂的方式講一次

想像一條走廊，走到底就是「這件事做完了」。走廊上有幾道關卡，每一關都要交出一樣東西才過得去，而那樣東西不能自己寫。

沒有這條走廊的時候，事情長這樣。你請一個很會寫程式的幫手做一件事，它做完跟你說「好了」。你問它測試過嗎，它說測過了。你信了，把它接到下一件事上。三天後你才發現，它測的是三個版本以前的程式碼。

它沒有騙人。「做完了」這句話誰都能說，說的時候不需要附上任何東西，所以它幾乎不用付出什麼。

ForgePilot 做的事，就是讓這句話說出口之前得先交出證據。

它自己不寫程式，也不判斷程式碼好不好，那些是你和你的 agent 的事。它站在關卡旁邊清點東西，少了什麼就直接說出少的是什麼。

聽起來很煩。一個從來不擋人的流程，跟沒有流程差不多。

02

完成條件，少一個就走不到底

測試通過的，是你正在看的那一版

每次驗證都綁死一個 immutable Candidate：既有 commit 或 working-tree snapshot，由 repository 自己的 make verify 在隔離的 checkout 裡跑。驗證通過才算數，而且結果誰都不能改寫。

Evidence · exact Candidate

沒有懸著沒人決定的問題

遇到不該自己決定的事，開一道 Gate 把問題記下來。問題還開著，工作就過不去，而且誰都看得見它開著。

Gate

這個目標本身還在進行中

目標被取消的時候，底下的工作連驗證都不給開始，也不能再匯入新的節點。

Goal

（選用）有人真的看過並且同意

Goal 在匯入時可以要求 Approval：驗證通過後工作先進 REVIEW，要有一筆明確記下來的人工審查，寫著誰在什麼時候同意了哪一個 Candidate。沒人反對不算同意。

Approval Requirement

條件同時齊了，工作才進入 DONE。同一個瞬間，等著它的下一件工作變成可以開始，最後一件 DONE 時整個 Goal 也自動完成，中間沒有「A 完成了但 B 還沒被通知」的空檔。

03

跟 agent 一起工作的時候，它站在哪裡

把寫程式的工作交給 agent 之後，有兩件事會同時發生。它做得比你快，而且它也比你更容易說出「做完了」。

它手上同時握著三個角色，自己挑要做哪一件事，自己寫，自己宣布完成。這三件事只要有一件出錯，你通常要等到很後面才會發現。

agent 可以寫程式，但不能發給自己通行證。

ForgePilot 把那三個角色拆開。哪一件事現在可以做，由帳本的 next 決定；程式碼由 agent 寫；算不算完成，由證據（和需要人判斷時的人）決定。迴圈由 agent 自己跑，ForgePilot 不啟動它，只在每一步回答「下一個合法動作是什麼」。

一次完整的迴圈長這樣。agent 從問「現在該做什麼」開始，到交出證據為止，中間有兩個地方它一定過不去。

這樣一來，agent 每一輪都得先問一次 next，它拿到的是一件依賴已經清乾淨、確實輪到它的工作。做完之後它能做的最後一件事是跑驗證，把結果留下來；PASS 就是完成。

你要看的東西也跟著變少。不必回頭審每一次對話，只要看 status 上有沒有卡住的工作，以及卡住的原因是哪一個。

同一個 workspace 同時最多一件 RUNNING 或 VERIFYING，next 也只給一個動作，所以換 session 或換 agent 都能從帳本接手，不會有兩個 agent 各自認領不同的工作互相踩。

怎麼把 agent 接上去

ForgePilot 沒有 agent 外掛，也不去攔截誰在跑什麼。它就是一個 CLI，所以接法有兩種：把 repository 的 skills/claude-code/forgepilot/（Codex 是 skills/codex/forgepilot/）手動複製進 agent 的 skill 目錄，讓它照 next → start → 實作 → verify 推進；或把規則寫進 agent 每次都會讀的那份指示檔，CLAUDE.md、AGENTS.md 或你的工具用的那一份都行。四條就夠了，規則本身建議用英文寫，指令與 flag 都是英文，混著中文敘述反而多一層轉換。

 貼進 AGENTS.md
## How work is picked up in this repo

1. Every round starts with `forgepilot next --json`. Act only on
   the `action` it returns, then ask again. If it says WAIT, NONE,
   GOAL_ALREADY_COMPLETED or GOAL_CANCELLED, stop and tell a human.
   Never pick your own next task.
2. Claim it with `forgepilot start <work-id>`. Do not skip this.
3. Never report "done". When you believe the work is finished, run
   `forgepilot verify <work-id>` (or `--snapshot` for uncommitted
   work) and paste the output verbatim. The evidence speaks for the
   work; your summary does not.
4. When a decision is not yours to make, run `forgepilot gate open`
   with the question and the options, then stop and wait. Never
   pick an option and carry on.

`gate resolve` and `review approve` are human decisions, never yours.

第四條最容易被忽略，它也是這套東西真正改變的地方。agent 卡住的時候原本會自己選一條路走下去，現在它把問題留在佇列上，你下次看 status 就會看到。

最後那句要說清楚它靠什麼成立。ForgePilot 不認證身分，agent 技術上跑得動 gate resolve 與 review approve，所以那是一句約定，不是一道鎖。真正擋著的是完成條件：DONE 只會是 verify 在確切 Candidate 上 PASS 的結果，沒有任何指令能直接寫入；approve 就算被跑了，最新 PASS 不是目前的 Candidate、或還有 Gate 開著，approve 會被拒絕、什麼都不寫，工作照樣不會進 DONE。條件滿足而真的通過的那一次，決定者會以它的 git 身分標示為「自述」留在記錄裡，跑不掉。

接下來的事跟你手動用一模一樣，安裝與 init 之後把上面四條貼進去就能開始。

04

被擋下來的時候，它會說出還差什麼

最容易讓人愣住的是這種情況。在要求 Approval 的 Goal 裡，測試明明過了，你正要按同意，工作卻不讓你完成。

因為在那兩件事之間，又有人 commit 了一次。通過測試的是舊的那一版，你要同意的是新的那一版，兩邊對不上。

ForgePilot 不會假裝沒事讓它過。它拒絕這次 approve，明說 PASS 已不是目前的 Candidate，並把該跑的指令印給你；next 同時會建議 REVERIFY。

再跑一次驗證，兩邊對齊，就過了。已經 DONE 的工作不會被這樣追溯，stale 只對等待審查的工作有意義。

05

從一個目標到 DONE，完整走一次

假設你要做的是把結帳流程的錯誤處理補起來。這件事會經過四個角色的手，先講清楚誰負責什麼，順序才不會記錯。

你

決定要做什麼、什麼時候算完成。把拆好的工單交成一份 Goal Plan、回答 Gate 上的問題，要求 Approval 的 Goal 還要做最後的 review。

Warrant

定義工程契約。Story 的格式（Goal、Out of Scope、Acceptance Criteria）、Story 要經人核准、完成要由 repo 自己的驗證命令證明，都寫在它那邊。它是規範，不是執行者。

agent

跑迴圈：問 next、讀 Story、照著規範寫程式、呼叫 verify。它不挑工作，也不宣布完成。

ForgePilot

判定下一步、擋人、記錄。真正去跑驗證並把結果綁在 immutable Candidate 上的是它，但跑什麼內容不由它決定。

前置規範與 Graph 形成。 這套流程在我們的實務中稱為 Graph Engineering：上游完成嚴格的 ADR → Spec → Story 拆分，以 ADR 確定架構決定，以經人核准的 Warrant Story 確定 Acceptance Criteria。隨後 ForgePilot 接入：拆好的工單寫成一份 Goal Plan（JSON，節點 ID 即 Work Item ID、每個節點指向一份 Story 並宣告 depends_on），goal import 一次建立 Goal 與整張有向無環圖（DAG）。計畫有環、依賴未知或 Story 路徑不存在，整份都不寫入；依賴未滿足的工作讀取時就是 PENDING，消除任何猜測與順序混亂。

agent 問下一件。 它跑 next，拿到的是依賴已經清乾淨、確實輪到的那一件，然後 start 認領。它不自己挑，也挑不到還卡著依賴的工作；同一時間只有一件工作能佔著位置。

寫程式，選擇 Candidate。 有兩條合法路徑：先 commit，再用 verify 驗證乾淨工作樹的 HEAD；或用 verify <work-id> --snapshot 把目前 working tree 固定成 immutable snapshot 後驗證。前者的工作樹只要還有未提交內容（含未追蹤檔案）就會拒絕，而且不寫 Evidence；那是無法驗證，不是驗證失敗。

隔離驗證，PASS 即完成。 Agent 實作後呼叫 verify：commit mode 在隔離 worktree 驗證 HEAD；snapshot mode 先把 working tree 固定成 immutable snapshot，再在隔離 checkout 執行 repo 自己 Makefile 的 verify target。跑的內容由 repo 自己決定，ForgePilot 不定義驗證，也不讀程式碼判斷對錯，它只負責真的跑一次，把 PASS、FAIL 或 INTERRUPTED 連同 Candidate revision 記成 Evidence。預設的 Goal 在 PASS 的那一刻工作就是 DONE；FAIL 則留在 RUNNING，next 轉為 REPAIR，讀 log、修好再驗證。

需要人的時候才有人。 如果 Goal 要求 Approval，PASS 先進 REVIEW，你 review approve，工作才在那一刻進 DONE；Candidate 在這之間變了就會被拒絕，要重新驗證。不要求 Approval 的 Goal 沒有這一步，沒有任何指令能替工作直接寫入 DONE。

拓撲推進到全圖完成。 agent 再問一次 next，推進下一個已解鎖節點。ForgePilot 始終握有順序與合法性的判定權，直到整個 Graph 的所有節點 DONE、Goal 自動完成，next 回報 GOAL_ALREADY_COMPLETED，迴圈結束。中間任何時候遇到不該自己決定的事，gate open 把問題留在帳本上停住，等你回答。

兩個最常被記反的地方。不帶 flag 的 verify 要先 commit；要保留 working tree 就用 verify --snapshot。PASS 就是完成，沒有另一道「宣告完成」的手續；只有要求 Approval 的 Goal，PASS 才會先停在 REVIEW 等人點頭。

全部是本機的命令列，不需要伺服器，也不需要帳號。狀態存在你 repo 裡的一個 JSON 檔，由程序鎖保護，多個終端機或多個 agent 同時用不會打架。

同一條路線的指令對照

init

在 repo 裡建立狀態檔。它會動到 .gitignore；若接著走 commit mode，先把它 commit。要驗證尚未提交內容時可改用 verify --snapshot。

goal import

用一份 Goal Plan 一次宣告目標與整張 DAG，寫清楚誰依賴誰。依賴還沒完成的工作讀取時就是等待狀態，不用你自己記；補單時改計畫檔再匯入，只能新增節點。

next

問它現在該做哪一件。這是純查詢，只給一個動作，不會偷偷把工作認領給你，而且它會說出為什麼選中這一件。

start

開始，工作成為 RUNNING 並佔住位置。這時候你或你的 agent 才真正去寫程式，ForgePilot 在這一段完全不插手。

verify

它在一個隔離的工作區裡，對確切 Candidate 跑那個 repo 自己 Makefile 裡的 verify target。不帶 flag 時 Candidate 是乾淨 HEAD；--snapshot 時是由目前 working tree 固定的 immutable snapshot。連 Makefile 存不存在都是在那份 checkout 裡判斷的，被 gitignore 掉的 Makefile 騙不過它。結果連同 Candidate revision 一起存起來，PASS 就是 DONE。

gate

做到一半發現有件事不該自己決定，就把問題和選項寫下來，工作停在那裡等人。它想養成的習慣就是這個，問題交出去，不要自己挑一個繼續做。

review

只用於要求 Approval 的 Goal：人看過之後同意或退回，理由留在檔案裡。條件齊了就完成並解鎖下游；Candidate 已 stale 就拒絕並告訴你該重新 verify。

status

把所有東西攤開。沒有驗證、沒有審查都會被明講出來，而且對每件未完成的工作說明為什麼不能前進，不會用留白帶過。沉默的缺席會被讀成沒問題的結果。

06

它刻意不做的事

  • 不寫程式，也不啟動你的 agent。寫程式、跑迴圈的還是它們，ForgePilot 只判定哪件事現在可以動，以及它算不算完成。
  • 不發出任何網路請求。除了 Git 與你的 make verify，它不啟動任何程序，也不持有任何憑證。
  • 不驗證身分。審查者的名字來自你的 git 設定，所以每次都明白印上「自稱」兩個字，免得誰把它當成簽章。
  • 完成之後不能反悔。DONE 是終點，沒有重開。要再動就開一件新工作，把歷史留著。
  • 狀態是一個檔案。程序鎖加上原子替換，跨終端機、跨 session、關掉再開都讀得回同一份事實。
  • 驗證的內容由你定義。它固定跑 make verify，內容與 toolchain 版本都是那個 repo 自己決定的，ForgePilot 只負責在乾淨且隔離的環境裡執行並如實記錄。
  • 記錄只增不改。通過、退回、被中斷的驗證都並排留著，「測試沒過」跟「人不接受」是兩件不同的事。
  • 每個不易反轉的決定都寫成 ADR，附上它在什麼條件下會失效。你可以不同意，但不會找不到理由。
07

開始

需要 Go 1.25.5 以上，用 go install 安裝，沒有外部相依。目前只宣稱支援 macOS 的本機檔案系統，因為程序鎖用的是作業系統的 flock，其他平台還沒實際驗證過。

裝好之後，使用手冊會帶你從 init 一路走到 DONE，包含每一個會擋住你的地方。裡面所有輸出都是真的跑出來貼上去的，不是寫出來的範例。

ForgePilot 是 AI 輔助軟體工程的被動 DAG 帳本，保存工作狀態、人工決策與驗證證據，讓工程工作能跨 agent 與 session 延續。它不取代 Warrant，也不啟動或取代你的 coding agent。

文件與實際行為不符時以程式碼為準。每一條流程在 integration_test.go 都有一個以獨立 process 對真實 git repository 執行的測試。
