ForgePilot · Architecture & State Internals

底層原理與狀態管理架構手冊

ForgePilot 是一套純標準庫構建的本機被動 DAG 帳本。它不寫業務程式碼、不用資料庫、不跑背景服務、不啟動 Agent，而是透過 POSIX 檔案鎖與純函數狀態機，讓「做完了」這句話綁定一個確切的 Candidate 與一筆不可竄改的 Evidence。

01 分層邊界與單向依賴

系統由幾個高內聚 Package 組成。核心原則是：「所有外圍 I/O 與 Subprocess 隔離在外，純領域狀態機不依賴任何外部介面」。

1. CLI 表現層 (internal/cli) Glue & Presentation

負責 flag 解析、人類閱讀終端排版、錯誤碼對應。自身絕不判定狀態轉移合法性，只負責將參數與外部事實傳入下層。

2. Orchestration 層 (internal/app) verify & goal import

verify 與 goal import 的流程只有這一份，internal/cli/verify.go 是薄殼。唯一可以同時碰 work、storage、repository 的地方。

3. Storage 交易層 (internal/storage) FLock + Snapshot

專案唯一的持久化引擎。負責跨行程 OS 檔案鎖、單一 JSON 快照反序列化、驗證與原子落地替換。

4. Repository 轉接層 (internal/repository) Git & Worktrees

全專案唯一允許呼叫 Git 的地方。負責 Story 路徑檢查、Candidate Snapshot 擷取、隔離臨時工作樹建立，以及啟動 canonical make verify。

5. 程序層 (internal/process) Process Groups

make verify 會 fork；程序群組的啟動、有界停止與停止確認放在這裡，只終止 leader 會讓真正的工作繼續跑。

6. 純領域核心 (internal/work) Pure State Machine

純領域邏輯：Goal Plan 驗證、狀態轉移、readiness、next 判定。零 Interface、零檔案讀寫、零 Git、零 Process 呼叫。所有外部事實（當前時間 now、測試 Exit Code）均以純值傳入，保證 100% 確定性可測。

02 狀態是用什麼管理的？底層儲存原理

無資料庫架構

ForgePilot 不使用 SQLite，也不使用任何嵌入式 Key-Value Store。所有 Goal、Work Item、Evidence 與 Gate，皆序列化保存在專案根目錄的單一物理檔案：.forgepilot/state.json。目前的 schema 版本是 19；它只讀 19，沒有 migration 框架。

交易寫入流程（storage.Update）

當執行任何狀態修改指令（goal import, start, verify, gate open, review approve）時，底層嚴格走以下 8 步原子交易：

1
取得 OS 核心檔案排他鎖

透過系統呼叫 syscall.Flock(fd, syscall.LOCK_EX) 鎖住 .forgepilot/locks/state.lock。若行程異常崩潰，作業系統會自動回收該鎖，絕不殘留死鎖。

2
反序列化載入記憶體

讀取 state.json，透過 json.NewDecoder 嚴格解析進 work.State 記憶體結構體（拒絕未知欄位），並檢查 SchemaVersion。

3
執行純邏輯閉包

執行傳入的 operation(&state) 函式。進行狀態檢查、轉移、Evidence 記錄，以及 Goal 的自動完成。

4
全域一致性防護（Validate）

呼叫 state.Validate()，在記憶體中掃描整個 DAG，保證沒有 Cycle、沒有未知 ID、沒有孤兒關聯。

5
寫入隔離臨時檔

os.CreateTemp(".state-*.tmp")，將帶縮排格式的 JSON 寫入臨時檔案。

6
硬體刷盤 (fsync)

呼叫 temporary.Sync() 強制實體硬盤將快取刷入磁碟，確保斷電時不遺失資料。

7
POSIX 原子重命名覆蓋

呼叫 os.Rename(temporaryName, "state.json")。利用 POSIX 原子性保證：讀取者要麼讀到前一個完整的狀態，要麼讀到新狀態，絕對不會讀到寫入一半被截斷的壞檔。

8
目錄刷盤與釋放鎖

目錄 handle dir.Sync() 確保目錄索引元數據落盤，最後 syscall.Flock(LOCK_UN) 釋放排他鎖。

03 工作狀態機與不可繞過的完成條件

Work Item 持久化的狀態只有五個：NOT_STARTED、RUNNING、VERIFYING、REVIEW、DONE。你在 status 看到的 PENDING / READY 是讀取時依「依賴是否全部 DONE」算出的投影，從不保存，所以沒有 reconcile，也沒有需要被補寫的欄位。

PENDING --(deps DONE)--> READY --start--> RUNNING --verify--> VERIFYING
                                             ^                    |
                                             +- FAIL/INTERRUPTED -+
                                                                  | PASS
  approval not required:  DONE <----------------------------------+
  approval required:      REVIEW <--------------------------------+
                          |-- approve --> DONE
                          +-- reject  --> RUNNING

為什麼沒有 forgepilot done 指令？

在 ForgePilot 中，DONE 永遠不能由任何人手動直接設置（ADR-0008 仍成立的部分）。它只能是 verify PASS（或要求 Approval 時的 review approve）在同一次受鎖交易內通過狀態機檢查後的結果：

進入 DONE 的條件

  • 1. 確切 Candidate 上的驗證通過：最新 Verification 為 PASS，且綁定的就是目前的 Candidate
  • 2. 零未解除 Gate：該工作沒有 OPEN 的 Gate（所有決策關卡都必須為 RESOLVED 或 CANCELLED）
  • 3. 目標有效性：所屬 Goal 必須處於 ACTIVE 狀態
  • 4. （選用）人工核准：Goal 以 require_approval 匯入時，PASS 先進 REVIEW，review approve 在記錄 APPROVED 的同一次交易內再檢查 1–3，才轉為 DONE

同交易解鎖與 Goal 自動完成

當一件工作晉升為 DONE，底層在同一個記憶體結構與同一筆 storage 寫入交易中檢查它所屬的 Goal 是否已全部 DONE：

func (s *State) complete(id string, now time.Time) {
    item := s.item(id)
    item.Status, item.UpdatedAt = Done, now
    s.completeGoalIfFinished(item.GoalID, now) // 全部節點 DONE 時，Goal 在同一筆交易轉為 COMPLETED
}

下游的 READY 不必寫入：它在每次讀取時由「依賴是否全部 DONE」算出，所以 A 一寫成 DONE，B 的 READY 就已經成立。這徹底解決了「A 工作已完成，但 B 工作在另一個行程讀取時仍顯示為等待」的中間競爭狀態。

next：只回傳一個合法動作

next 是 domain state 加上目前 repository facts 的純讀 projection，不持久化，也從不替 Agent 執行建議。判定順序固定：先看佔住 workspace 的工作（REPAIR / RESUME / RECOVER / WAIT），再看 stale 的 REVIEW 工作（REVERIFY），再看最早的 READY 且無未解除 Gate 的工作（START），最後才是等人（WAIT）或已結束（GOAL_ALREADY_COMPLETED / GOAL_CANCELLED / NONE）。有佔位時跳過 REVERIFY 與 START，因為它們推薦的 transition 會被單一佔位規則拒絕。

04 驗證隔離與 Candidate Snapshot 原理

ForgePilot 的 verify 從不在使用者的工作樹中直接跑測試。因為工作區中可能有未存檔修改、未編譯的雜檔，直接執行測試毫無證據公信力。

A
固定 Candidate 候選版本

可以是既有的 Git Commit SHA；若是使用 verify --snapshot，系統會利用 Private Git Index 擷取當前未 commit 的變更，寫入 refs/forgepilot/snapshots/*，不產生污染 git log 的 WIP commit，也不改動當前分支的 HEAD。

B
建立獨立的 Detached Worktree

在 .forgepilot/worktrees/<work-id>-<short-sha> 建立隔離的臨時工作樹，完全獨立於使用者編輯器與 shell 環境。受驗專案的 make verify 因此必須能在全新 checkout 上執行。

C
由專案自己固定 toolchain

ForgePilot 不解析 .node-version、go.mod 這類 runtime 宣告，也不管理工具鏈版本；檢查繼承呼叫者的環境，toolchain 版本由受管理專案的 make verify 自己固定。

D
執行 canonical make verify 並即時串流

執行專案標準驗證指令，stdout/stderr 即時落地至 .forgepilot/logs/（以 run 為鍵，ADR-0012），測試完畢後立即回收臨時工作樹，並將 PASS/FAIL/INTERRUPTED 結果固化成不可變的 Evidence。一次 verify 只為觸發它的那件工作留下 Evidence。

05 邊界劃分：做到哪裡 vs 堅決不做什麼

維度 ForgePilot 做到哪 (In-Scope) 堅決不做什麼 (Out-of-Scope)
程式碼產出 固定候選版本（Commit / Snapshot SHA） 不寫業務程式碼、不啟動 Agent、不替代工程師或 AI Agent 思考
需求與規格 只儲存 story_ref 路徑指針與依賴關係；由 Goal Plan 匯入整張 DAG 不定義規格細節，也不拆單；規格完全委派給外部 PraxisBound
驗證執行 在隔離 Worktree 執行專案自身的 make verify 並留痕 不自行猜測驗證指令、不解析 runtime，測試失敗不自動修復程式碼
決策與關卡 Gate 記錄分歧選項（至少 2 個）與決策者自述身分 不做假權限登入（ADR-0005），不自動核准決策
外部整合 完全離線；除 Git 與 make verify 外不啟動任何程序 零網路請求（ADR-0010），不呼叫 GitHub API，也沒有 PR 欄位
狀態終態 條件滿足時推至 DONE，並解鎖下游、完成 Goal DONE 絕不允許 Reopen（ADR-0006），不代執行 Git Merge / Push
