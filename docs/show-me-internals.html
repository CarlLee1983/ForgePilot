ForgePilot · Architecture & State Internals

底層原理與狀態管理架構手冊

ForgePilot 是一套純標準庫構建的本機工程狀態機與決策證據引擎。它不寫業務程式碼、不用資料庫、不跑背景服務，而是透過嚴格的 POSIX 檔案鎖與純函數狀態機，讓「做完了」這句話真正具備不可篡改的法律約束力。

01 分層邊界與單向依賴

系統由四個高內聚 Package 組成。核心原則是：「所有外圍 I/O 與 Subprocess 隔離在外，純領域狀態機不依賴任何外部介面」。

1. CLI 表現層 (internal/cli) Glue & Presentation

負責 flag 解析、人類閱讀終端排版、錯誤碼對應。自身絕不判定狀態轉移合法性，只負責將參數與外部事實傳入儲存與領域層。

2. Storage 交易層 (internal/storage) FLock + Snapshot

專案唯一的持久化引擎。負責跨行程 OS 檔案鎖、單一 JSON 快照反序列化、驗證與原子落地替換。

3. Repository 轉接層 (internal/repository) Git & Worktrees

全專案唯一允許呼叫 Git 的地方。負責 Candidate Snapshot 擷取、隔離臨時工作樹建立、Runtime 工具鏈版本解析。

4. 純領域核心 (internal/work) Pure State Machine

純領域邏輯。零 Interface、零檔案讀寫、零 Git、零 Process 呼叫。所有外部事實（當前時間 now、測試 Exit Code）均以純值傳入，保證 100% 確定性可測。

02 狀態是用什麼管理的？底層儲存原理

無資料庫架構

ForgePilot 不使用 SQLite，也不使用任何嵌入式 Key-Value Store。所有 Goal、Work Item、Evidence 與 Gate，皆序列化保存在專案根目錄的單一物理檔案：.forgepilot/state.json。

交易寫入流程（storage.Update）

當執行任何狀態修改指令（start, verify, gate open, review approve）時，底層嚴格走以下 8 步原子交易：

1
取得 OS 核心檔案排他鎖

透過系統呼叫 syscall.Flock(fd, syscall.LOCK_EX) 鎖住 .forgepilot/locks/state.lock。若行程異常崩潰，作業系統會自動回收該鎖，絕不殘留死鎖。

2
反序列化載入記憶體

讀取 state.json，透過 json.NewDecoder 嚴格解析進 work.State 記憶體結構體，並檢查 SchemaVersion。

3
執行純邏輯閉包

執行傳入的 operation(&state) 函式。進行狀態檢查、轉移、Evidence 記錄，以及依賴連鎖解鎖。

4
全域一致性防護（Validate）

呼叫 state.Validate()，在記憶體中掃描整個 DAG，保證沒有 Cycle、沒有未知 ID、沒有孤兒關聯。

5
寫入隔離臨時檔

os.CreateTemp(".state-*.tmp")，將帶縮排格式的 JSON 寫入臨時檔案。

6
硬體刷盤 (fsync)

呼叫 temporary.Sync() 強制實體硬盤將快取刷入磁碟，確保斷電時不遺失資料。

7
POSIX 原子重命名覆蓋

呼叫 os.Rename(temporaryName, "state.json")。利用 POSIX 原子性保證：讀取者要麼讀到前一個完整的狀態，要麼讀到新狀態，絕對不會讀到寫入一半被截斷的壞檔。

8
目錄刷盤與釋放鎖

目錄 handle dir.Sync() 確保目錄索引元數據落盤，最後 syscall.Flock(LOCK_UN) 釋放排他鎖。

03 工作狀態機與五道不可繞過的完成防線

Work Item 的生命週期由 6 個離散狀態組成：

PENDING ──(依賴滿足)──▶ READY ──(start)──▶ RUNNING ──(verify)──▶ VERIFYING
                                                                     │
                                                       (PASS 產出 Evidence)
                                                                     ▼
DONE ◀──(review approve, 條件全足)── REVIEW ◀────────────────────────┘

為什麼沒有 forgepilot done 指令？

在 ForgePilot 中，DONE 永遠不能由任何人手動直接設置（ADR-0008）。它只能是在 review approve 執行時，由狀態機底層 CompletionBlockers(id) 檢查通過後的推論結果：

CompletionBlockers 檢查清單

  • 1. 最新審查必須通過：LatestReview(id).Result == APPROVED
  • 2. 最新驗證必須通過：LatestVerification(id).Result == PASS
  • 3. 雙向版本 SHA 精確錨定：Verification.Revision == Review.Revision（測試 PASS 的 commit 與人審查的 commit 必須一模一樣）
  • 4. 零未解除 Gate：OpenGateCount(id) == 0（所有決策關卡都必須為 RESOLVED）
  • 5. 目標有效性：所屬 Goal 必須處於 ACTIVE 狀態

同交易連鎖解鎖（Cascade Ready）

當一件工作晉升為 DONE，底層在同一個記憶體結構與同一筆 storage 寫入交易中呼叫 s.RefreshReady(now)：

func (s *State) complete(id string, now time.Time) {
    item := s.item(id)
    item.Status, item.UpdatedAt = Done, now
    s.RefreshReady(now) // 重新走訪 DAG，所有依賴皆 DONE 的 PENDING 節點立即翻轉成 READY
}

這徹底解決了「A 工作已完成，但 B 工作在另一個行程讀取時仍顯示為等待」的中間競爭狀態。

04 驗證隔離與 Candidate Snapshot 原理

ForgePilot 的 verify 從不在使用者的工作樹中直接跑測試。因為工作區中可能有未存檔修改、未編譯的雜檔，直接執行測試毫無證據公信力。

A
固定 Candidate 候選版本

可以是既有的 Git Commit SHA；若是使用 verify --snapshot，系統會利用 Private Git Index 擷取當前未 commit 的變更，寫入 refs/forgepilot/snapshots/*，不產生污染 git log 的 WIP commit，也不改動當前分支的 HEAD。

B
建立獨立的 Detached Worktree

在 .forgepilot/worktrees/run-* 建立隔離的臨時工作樹，完全獨立於使用者編輯器與 shell 環境。

C
確定性運行時探索 (Deterministic Runtime Resolution)

從 Candidate 內的 .node-version, go.mod 等檔案解析宣告的版本要求，於本機已安裝的工具鏈中找到精確匹配者，防止 caller shell 的 PATH 造成測試污染。

D
執行 canonical make verify 並即時串流

執行專案標準驗證指令，stdout/stderr 即時落地至 .forgepilot/logs/<run-id>.log（ADR-0012），測試完畢後立即回收臨時工作樹，並將 PASS/FAIL 結果固化成不可變的 Evidence。

05 邊界劃分：做到哪裡 vs 堅決不做什麼

維度 ForgePilot 做到哪 (In-Scope) 堅決不做什麼 (Out-of-Scope)
程式碼產出 固定候選版本（Commit / Snapshot SHA） 不寫業務程式碼、不替代工程師或 AI Agent 思考
需求與規格 只儲存 story_ref 路徑指針與依賴關係 不定義規格細節，規格完全委派給外部 ForgeFlowV2
驗證執行 在隔離 Worktree 執行專案自身的 make verify 並留痕 不自行猜測驗證指令，測試失敗不自動修復程式碼
決策與關卡 Gate 記錄分歧選項（至少 2 個）與決策者自述身分 不做假權限登入（ADR-0005），不自動核准決策
外部整合 PR Reference（owner/repo#123）作為審查標註 零網路請求（ADR-0010），不呼叫 GitHub API 查證 PR
狀態終態 條件全部滿足時自動推至 DONE，並解鎖下游 DONE 絕不允許 Reopen（ADR-0006），不代執行 Git Merge / Push
