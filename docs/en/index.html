Passive DAG Ledger

Done is proven, not declared.

An AI agent can generate a lot of code in seconds, and can just as easily report "I'm done." ForgePilot does not trust any claim that comes without evidence.

It is not a dashboard, and it stays out of the coding itself. Its one job is to stop work from advancing when the verification evidence is missing, the working tree is dirty, or a human decision is still open, so that engineering work stays traceable.

The Cost of Certainty

When generating code is cheap, verification has to carry the weight.

When people wrote the code, the friction was in the writing. With agents, the biggest systemic risk is that declaring work done costs nothing.

When you hand engineering work to an AI agent, it usually holds too much at once: it picks the task, changes the code in your working tree, and announces that the tests pass. If any one of those steps hallucinates or misses something, you often find out only after the merge or the release.

ForgePilot separates those three roles.
Dependencies and next decide which work can start now. The agent writes the code. Whether the work is done is decided only by a real PASS recorded in an isolated checkout of the exact Candidate, plus a human approval when the Goal requires one. An agent saying it is finished never counts.

ForgePilot is fully offline. It makes no network requests and runs no remote database. Apart from Git and your make verify, it starts no processes, and it never launches an agent. Every fact it tracks lives in one state file protected by a process lock.

Immutable Gates

Four gates. Miss one and the work stays put.

These are state-machine checks, not a dashboard. If any one fact is missing, ForgePilot refuses to advance the work and says why.

Work Item · queue
next names the one item whose turn it is
Candidate · exact version
Pins the HEAD commit or a working-tree snapshot
Verification · isolated check
Runs your make verify in a clean, detached worktree
Gate · human decision
An open Gate blocks the work; PASS completes it and unlocks what depends on it
Real-world Graph Engineering

From ADRs, specs and Stories to a Work Item DAG

This loop comes from several rounds of dogfooding, not from theory. ADRs, specs and human-approved Warrant Stories settle the intent first. ForgePilot imports one Goal Plan as an executable dependency graph (DAG). An external agent follows next, and isolated verification, Evidence and explicit Gates keep the order traceable.

STAGE 01 ADR

Record decisions as ADRs

Every non-obvious trade-off and boundary is first written down as an Architecture Decision Record, with the conditions under which it would no longer hold, so it is not silently reversed later.

STAGE 02 Warrant

Split into specs and Stories

The goal is broken into specs and Stories with one responsibility each, carrying acceptance criteria and test contracts that define what "correct" means.

STAGE 03 ForgePilot

Import the Work Item DAG

goal import reads a Goal Plan and creates the Goal and its whole directed acyclic graph at once. A cycle, an unknown dependency or a missing Story path rejects the whole plan. Items whose dependencies are not DONE read as PENDING, and as READY once they are.

STAGE 04 Agent + ForgePilot

Implement, verify, complete

The agent implements and runs verify. ForgePilot runs the canonical check against an immutable Candidate. PASS means DONE and unlocks downstream work in the same transaction, and the Goal completes when its last item is DONE. If the Goal was imported with require_approval, PASS moves the item to REVIEW and a human's review approve makes it DONE.

One item at a time, verified in isolation

Once an item is claimed, the agent implements that Story's acceptance criteria and runs verify. ForgePilot runs make verify in an isolated checkout of the Candidate, and only that produces PASS Evidence. Only one item holds the workspace at a time.

Repair on failure, stop for people

After a FAIL the item stays RUNNING and next says REPAIR: read the log, fix it, verify again. When an architectural decision or an ambiguous spec comes up, the agent opens a Gate and stops until a person decides, instead of picking an option and carrying on.

Driven by the graph, not by guesses

The agent never has to guess what to do next. ForgePilot derives the one legal next action from the graph and the state machine, and the agent runs that loop until every node is done and the Goal completes.

Architectural Bounds

Three hard boundaries

The tool manages only what it owns, and leaves the decisions it should not guess to the people responsible for them.

01 / EVIDENCE

No Evidence, no done.

A verification result is always bound to an exact Candidate revision. Once the code changes, an old PASS never vouches for the new content.

02 / HUMAN DECISION

What people decide, the process does not guess.

A Gate gives a design question a name and a set of options, and pauses the work it is about. While the question is open, that work cannot complete, so nothing downstream unlocks.

03 / SEAM DISCIPLINE

The tool manages only what it owns.

Story intent belongs to Warrant, and code quality belongs to the repository's own checks. ForgePilot only tracks whether work can move forward right now.

Quickstart

Hand the facts to the next session.

Install with go install, run init in the repository you manage, and import a Goal Plan with goal import. From there an external agent works through the items one by one, following next.

Install instructions
TERMINAL QUICKSTART 
$ cd your-project
$ forgepilot init
Initialized ForgePilot in /your/project

$ forgepilot goal import plans/billing-sync.json
Goal billing-sync imported: 2 nodes
  schema READY specs/stories/schema
  sync-job PENDING specs/stories/sync-job

$ forgepilot next
Next: schema
State: READY
Goal: billing-sync
Story: specs/stories/schema
Action: forgepilot start schema
Reason: earliest READY work
