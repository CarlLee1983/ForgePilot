FORGEPILOT TECHNICAL SPECIFICATION · KEYNOTE DECK

ForgePilot：工程控制平面
與確定性狀態引擎

它不寫業務程式碼、不用外部資料庫、不跑 Daemon，也不依賴網路。它是一套只用 Go 標準庫構建的本機法官，專門管理工程工作的可執行性、進度佇列與決策證據，讓「做完了」這句話真正具備物理與法律約束力。

「當 Agent 面對歧義時最容易做的事，是自己選一個繼續往下寫；而『跑過測試了』如果沒有綁定確切不可變的 Commit SHA，它就只是一句無法查證的話。」

POSIX FLOCK

核心互斥保證

利用 OS 檔案系統鎖原語，跨 Process 排他互斥，進程崩潰時核心自動釋放，徹底杜絕死鎖與並發競爭。

SINGLE SNAPSHOT

原子狀態快照

單一 JSON 涵蓋 Goal、WorkItem、Evidence 與 Gate，透過 os.Rename POSIX 原語原子替換，零殘留破壞狀態。

ORTHOGONAL GATE

正交阻擋關卡

「阻擋不是一種狀態」（ADR-0007）。決策關卡獨立於生命週期，必須提供 2 個以上選項，由人類明確抉擇。

NO "DONE" COMMAND

無完成指令

沒有 forgepilot done 指令。DONE 只能是五道物理條件在同一次交易內同時成立時的客觀必然結果。

PARADIGM SHIFT · ARCHITECTURAL CONTRAST

工程失控的本質：狀態活在對話裡

在 AI 輔助軟體工程中，最致命的不是模型寫錯程式碼，而是「任務邊界混亂」與「口頭宣稱完成」。

傳統 Agent / 聊天模式的脆弱陷阱

對話上下文驅動（Ephemeral Context）

依賴 LLM 在 Context Window 裡記住哪些做完、哪些卡住。一旦 Context Compaction 或開啟新 Session，狀態瞬間失真遺失。

  • 自我評估測試結果（「我已經跑過測試且通過了」）
  • 遇到架構分歧時自行猜測選擇，缺乏人為審計痕跡
  • 工作尚未驗證即可口頭宣稱「已完成」，後續任務違規偷跑
  • 測試直接在骯髒的工作區執行，結果受未存檔檔案污染
  • 跨任務依賴關係混亂，常出現依賴項未就緒即開工
ForgePilot 確定性控制平面（Ground Truth）

本機檔案系統鎖 + 狀態機驅動

純值狀態機與受 POSIX 鎖保護的物理磁碟快照。任何動作都必須有不可篡改的證據（Evidence）為憑。

  • 測試結果必須來自隔離 Worktree 的 make verify 實體 Exit Code 0
  • 架構決策必須掛載 Gate，列出具體選項並由 Human Decision 留痕簽核
  • 沒有任何指令能手動將工作設為 DONE，條件缺一不可
  • 透過 Git Snapshot 隔離環境測試，不改動 HEAD 也絕不受雜檔干擾
  • DAG 嚴格依賴拓撲：前置工作未 DONE，下游永遠死守 PENDING
LAYER BOUNDARIES · COHESIVE PACKAGES

四層模組分層與責任單向性

Go 標準庫實作。所有外部 I/O、Subprocess 與檔案系統操作被隔離在外圍，純狀態機位於核心，保證 100% 確定性可測。

LAYER 1 · PRESENTATION

CLI 表現層 (internal/cli)

責任：終端參數解析、Flag 驗證、人類可讀排版與 Exit Code 映射。

✘ 絕不自行判定狀態流轉是否合法。
✔ 僅作為控制膠水，排程調度 Storage、Repository 與 Work。

LAYER 2 · PERSISTENCE

Storage 交易層 (internal/storage)

責任：OS 檔案鎖排他控制、單一 JSON 快照反序列化、原子寫入替換。

✔ 唯一的儲存入口：storage.Update(root, func(*work.State))。
✔ 跨實體原子交易，杜絕讀寫競爭與局部殘留狀態。

LAYER 3 · ADAPTER

Repository 轉接層 (internal/repository)

責任：專案中唯一允許呼叫 Git 的模組。

✔ 負責私有 Index 快照擷取 (Candidate Snapshot)。
✔ 建立臨時隔離的 detached worktree、解析 Candidate Runtime 要求。

LAYER 4 · CORE

純領域核心 (internal/work)

責任：純狀態機、依賴 DAG、候選選取 (Next) 與轉移防護。

零 Interface、零檔案讀寫、零 Git、零 Process 呼叫。
所有外部事實（時間、Exit Code）一律以純值參數傳入。

「如果一個狀態機需要 Mock 檔案系統或模擬 Git 才能測試，那它的責任邊界就已經混濁了。」

STORAGE ENGINE · ACID ATOMICITY

狀態是怎麼管理的？底層 8 步原子交易

無資料庫架構。所有狀態集中於 .forgepilot/state.json，透過 POSIX 系統呼叫達成嚴格的一致性。

internal/storage/storage.go · Atomic Read-Modify-Write Pipeline 
// storage.Update 執行的 8 步無損寫入管線
func Update(root string, operation func(*work.State) error) error {
    // [1] 取得 OS 核心檔案排他鎖 (Crash-Safe，進程終止由核心自動解除)
    return withLock(directory, func() error {
        // [2] 載入並反序列化當前完整快照
        state, _ := load(directory)

        // [3] 執行純記憶體領域邏輯 (狀態推進、產生 Evidence、連鎖解鎖)
        if err := operation(&state); err != nil { return err }

        // [4] 全域一致性防護檢查 (拒絕 cycle、重複依賴、無效關聯)
        if err := state.Validate(); err != nil { return err }

        // [5] 寫入隔離的暫存檔案: .state-*.tmp
        temporary, _ := os.CreateTemp(directory, ".state-*.tmp")

        // [6] 硬體刷盤 (fsync)，強制實體磁區落盤
        temporary.Sync()

        // [7] POSIX 原子重命名: os.Rename(tmp, "state.json")
        os.Rename(temporary.Name(), destination)

        // [8] 目錄元數據刷盤 & 釋放 syscall.Flock(LOCK_UN)
        return directoryHandle.Sync()
    })
}
零部分狀態 (NO PARTIAL STATE)

徹底消滅狀態撕裂

由於 os.Rename 在 POSIX 規範中是原子操作，任何外圍行程讀取時，要麼讀到前一個完整的 JSON，要麼讀到更新後的完整 JSON，絕對不可能讀到寫了一半被截斷的壞檔。

跨實體交易邊界

Goal + WorkItem + Evidence + Gate 同步

四者共用同一次受鎖替換。「完成一件工作」與「解鎖下游相依任務」必然落在同一次交易內，讀取者永遠不會看到「A 已 DONE 但依賴 A 的 B 仍處於 PENDING」的中間狀態。

STATE MACHINE · ORTHOGONAL DECISION GATES

工作狀態流轉與正交 Gate 阻擋模型

Work Item 的狀態精確描述其在工程生命週期中的坐標；而「阻擋」則由獨立的 Gate 表達，兩者維度正交。

STAGE 01

PENDING

工作已建立，但前置依賴尚未全部達成 DONE。佇列靜態等待。

條件：等待依賴推進
STAGE 02

READY

所有前置依賴全部達成 DONE，且無未解 Gate。可被 next 查詢認領。

動作：forgepilot start
STAGE 03

RUNNING

工程師或 AI Agent 正在撰寫程式碼與單元測試。進行實質變更。

動作：forgepilot verify
STAGE 04

VERIFYING

已鎖定 Candidate，正在隔離 Worktree 執行專案自身的 make verify。

產出：PASS Evidence
STAGE 05

REVIEW ➔ DONE

測試通過，等待人工審查。審查核准且條件全足時瞬間進入 DONE 終態。

終態：連鎖解鎖下游
常見反模式：把阻擋當成狀態

引入 BLOCKED 或 WAITING_HUMAN 狀態

一旦狀態欄被 BLOCKED 佔用，系統就必須被迫發明額外欄位去記住「被擋之前它究竟是 RUNNING 還是 VERIFYING」，在恢復時容易引發嚴重的狀態覆寫漏洞。

ForgePilot 原則 (ADR-0007)

Gate 與狀態完全正交

工作仍處於其正常狀態（如 RUNNING），阻擋僅由「該工作名下是否有未解除的 Gate」表達。Gate 提出時必須列出至少 2 個具體選項，由人類做出 Human Decision 留痕解除。

COMPLETION RIGOR · ZERO SHORTCUTS

完成是條件的結果，不是一個指令

產品中沒有 done，沒有 complete <id>，也沒有測試專用的跳步開關。唯有五道條件全部滿足，DONE 才會由系統自動推論達成。

internal/work/completion.go · CompletionBlockers Evaluation 
func (s *State) CompletionBlockers(id string) []string {
    // [條件 1] 最新人類審查必須存在且為 APPROVED
    review, reviewed := s.LatestReview(id)
    if !reviewed || review.Result != Approved { blockers = append(blockers, ...) }

    // [條件 2] 最新驗證必須存在且為 PASS
    verification, verified := s.LatestVerification(id)
    if !verified || verification.Result != Pass { blockers = append(blockers, ...) }

    // [條件 3] 雙向版本 SHA 必須 100% 精確相等 (同一 Commit 上既測過也被審過)
    if reviewed && verified && verification.Revision != review.Revision {
        blockers = append(blockers, "the latest PASS is at revision %s but approval is at %s")
    }

    // [條件 4] 工作名下不能有任何未解 Gate
    if count := s.OpenGateCount(id); count > 0 { blockers = append(blockers, ...) }

    // [條件 5] 所屬目標必須為 ACTIVE
    if goal := s.goal(item.GoalID); goal == nil || goal.Status != GoalActive { ... }

    return blockers // 唯有為空切片時，系統才放行進入 DONE
}
CASCADE READY

同交易連鎖解鎖

當某件工作完成時，在同一次交易內自動遍歷 DAG 執行 s.RefreshReady()，所有下游依賴滿足的工作立即翻轉為 READY，佇列自動推進。

EXACT-HEAD PR (M4)

PR 精確 HEAD 整合

Human Review 支援掛載 PR Reference（owner/repo#123），一旦 PR 產生新的 Commit，舊的 Review 立即過期失效，必須重審。

NO SILENCE

狀態不能沉默 (ADR-0008)

因為沒有手動 complete 指令，status 指令絕不能對未完成的原因保持沉默，必須具體印出到底差哪一道條件（例如差審查或 SHA 不合）。

CANDIDATE ISOLATION · DETERMINISTIC RUNTIME

Candidate 快照隔離與確定性驗證

ForgePilot 絕不在當前工作區直接執行驗證。工作區的雜檔、未提交變更與 shell PATH 污染，是測試不可信的罪魁禍首。

P0-001 CANDIDATE SNAPSHOT

私有 Index 快照擷取

使用 verify --snapshot 時，利用 Git Private Index 將當前暫存/未暫存變更直接壓入 refs/forgepilot/snapshots/*。

✔ 零 WIP Commit 污染 Git Log。
✔ 不動使用者分支、HEAD 與真實工作區。

ISOLATED WORKTREE

獨立 Detached 工作樹

在 .forgepilot/worktrees/run-* 建立獨立的 detached worktree。驗證完全在乾淨副本中執行，測試結束後自動清理回收。

✔ 驗證輸出串流即時寫入 .forgepilot/logs/。
✔ 即使終端被 Ctrl+C 中斷，也有孤兒回收機制。

P1-004 RUNTIME RESOLUTION

確定性工具鏈解析

主動從 Candidate 內的 .node-version、go.mod 探索 Runtime 契約，並於本機選取相符的二進制工具鏈。

✔ 絕不安裝或竄改使用者全域環境。
✔ 杜絕因不同終端 PATH 預設版本不同導致的測試偏差。

「不可變的程式碼身分（Candidate SHA）＋確定性的運行時版本（Resolved Runtime），才能產生不可篡改的工程證據（Evidence）。」

AUTHORITY BOUNDARIES · DISCIPLINED SCOPE

責任邊界：它做到哪，堅決不做什麼？

ForgePilot 的力量來自於其嚴苛的克制。以下是經由 14 份 ADR 所確立的鋼鐵邊界。

維度 ForgePilot 做到哪 (In-Scope) 堅決不做什麼 (Out-of-Scope)
任務與狀態 維護依賴拓撲 DAG，判定任務何時可開工 (READY) 與完成 (DONE)。 DONE 絕不允許 Reopen (ADR-0006)。要重做必須新開 Work Item 留存脈絡。
需求規格 只儲存 story_ref 路徑指針。 不複製規格內容，規格完全交由 ForgeFlowV2 或文件管理 (ADR-0013)。
決策關卡 Gate 記錄分歧選項（至少 2 個）與決策者自述審計身分。 不做半套認證 (ADR-0005)。本機 CLI 的身分驗證是假安全，不如誠實記錄。
網路與外部整合 PR Reference (owner/repo#123) 作為審查身分識別。 零網路請求 (ADR-0010)。不呼叫 GitHub API、不查證 PR 是否存在，純離線運作。
程式碼與交付 固定 Candidate SHA，在隔離環境跑 make verify 存證。 不代為 Git Merge 或 Push。DONE 僅代表驗收合格，不等於 Release 授權。

「ForgePilot 唯一的職責就是當一名剛正不阿的本機法官。它不在乎程式碼是人類寫的還是 AI 寫的，只要證據不足，誰也別想跨過完成這道門。」
