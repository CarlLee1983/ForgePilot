ForgePilot · Engineering Control Plane

它不寫程式。
它決定什麼可以開始、什麼算完成。

一個只用 Go 標準函式庫的本機 CLI，管理工程工作的可執行性、進度，以及每一個判斷的證據。M1–M4 已全部實作。

問題

Agent 輔助的工程有一個特定的失效模式：狀態活在對話裡。哪件事可以開始、哪件事在等誰的判斷、某次「測試通過了」是在哪一版通過的——這些都留在某次 session 的上下文中，換一個 session 就沒了。

後果不是效率問題，是可信度問題。Agent 面對規格歧義時最容易做的事，是自己選一個然後繼續往下寫；而「跑過測試了」如果沒有綁定確切的 commit，它就只是一句話。

ForgePilot 的位置

它不產生 Story、不用 LLM 判斷 PASS、不決定架構、不 merge 也不 release。工程要求由 ForgeFlowV2 定義，正確性由 repository 自己的 make verify 判斷，該由人決定的事由人決定。ForgePilot 只負責把這些事實記下來，並且擋住不該推進的工作。

核心概念

Goal

需要跨多次工程工作推進的長期目標。有 ACTIVE / BLOCKED / COMPLETED / CANCELLED 四個狀態，COMPLETED 必須人手動宣告且要求底下全部工作皆已完成。

Work Item

歸屬一個 Goal、參照一個 ForgeFlow Story 的工作單位，有自己的狀態與依賴。它只保存 story_ref，不複製 Story 的需求。

不是另一種獨立的 Task 物件，也不是 Story 的副本。

Gate

依附於單一 Work Item、需要明確人為決定才能解除的關卡。提出時必須列出至少兩個選項。未解除的 Gate 擋住那件工作推進，但不改變它的狀態。

不是驗證失敗，也不是逾時就自動同意。

Evidence

綁定一件工作與一個確切 Candidate revision 的紀錄，只新增不修改；Candidate 可以是既有 commit 或 working-tree snapshot。兩種：Verification（PASS / FAIL / INTERRUPTED）與 Human Review（APPROVED / REJECTED），共用同一條時間軸。

不是完成宣告，也不是 Agent 的自評。

Human Review

人對某個確切 revision 記錄的判斷。M4 起可以額外指明它發生在哪個 pull request 上。

不是Verification PASS，也不是 merge 授權。

完成是條件的結果，不是一個指令

產品裡沒有 done，沒有 complete <work-id>，也沒有測試專用的捷徑。DONE 只會在 review approve 記錄審查的同一次交易內、四項條件同時成立時發生：

forgepilot review approve WI-001
  ├─ 記錄 APPROVED Evidence          ← 一定會發生，先審後驗是正當流程
  └─ CompletionBlockers(WI-001) 是空的嗎？
       ├─ 同一 revision 的最新 Verification 是 PASS
       ├─ 最新 Human Review 是 APPROVED
       ├─ 沒有未解除的 Gate
       └─ Goal 是 ACTIVE
     ── 全部成立 ─▶ DONE + RefreshReady()   同一次交易，下游立刻 READY
     ── 有一項不成立 ─▶ 停在 REVIEW，status 說出差的是什麼

最後一行不是客套。因為沒有完成指令，status 是使用者唯一能得知「為什麼還沒完成」的地方，所以它不能對未完成的原因沉默——這條被測試釘住。

四個 milestone

M1

Durable Engineering Queue

Goal、Work Item、依賴、狀態轉移、deterministic 的 next-work selection，以及受程序鎖保護的原子 JSON state。跨 process 保存一致。

M2

Verification Evidence

M2 在隔離的 detached worktree 對乾淨 HEAD 執行受管理專案自己的 make verify，結果存成綁定該 revision 的 Evidence。P0-001 再加入 --snapshot，把 working tree 固定成 Candidate 後走同一條驗證路徑。新 Candidate 不沿用舊的 PASS。

M3

Human Gate & Review

Gate 擋住需要人判斷的工作，Human Review 記錄 APPROVED / REJECTED，完成與下游解鎖落在同一次交易內。佇列第一次真的會前進。

M4

PR exact-head review

Human Review 可以額外攜帶 owner/name#number，讓日後回頭讀這筆紀錄的人找得到當時的討論。刻意的小增量：沒有新增任何狀態機行為。

幾個關鍵決定

ADR-0007

阻擋不佔用狀態欄

沒有 WAITING_HUMAN，Work Item 也沒有 BLOCKED。狀態描述工作在生命週期的位置，Gate 是另一個維度的條件。兩處各表達一次同一事實，就會需要「記住進入阻擋前是什麼狀態」這種只為修補覆寫而存在的欄位。

ADR-0006

DONE 是終態，沒有 reopen

它記錄的是已經發生的事，後續 commit 不使其失效。需要重做就新增一件 Work Item，讓「為什麼重做」有地方被記錄。也因此 DONE 的工作不標示 stale——那個提示對它不對應任何行動。

ADR-0005

身分是自述的，不做認證

決策者預設取自 git config user.email，並在每一處輸出明確標示為聲明。半套的認證比不做更危險——它會讓人以為那個名字有保證。

ADR-0009

回收先於拒絕

verify 先無條件把上次被中斷的執行記為 INTERRUPTED，再判斷能不能開始新的一次。中斷是已經發生的事實，不該被任何阻擋條件扣住；能不能再跑一次，才是阻擋條件要回答的問題。

ADR-0010

不主動發出網路請求

不自行 HTTP，也不 spawn gh。PR 是使用者輸入的識別字串，只驗格式。代價是標錯不會被偵測；換來的是這個工具在沒有網路、沒有 token、GitHub 掛掉時照樣可用，而 Evidence 的結果集合不必為「遠端不可用」再開一個值。

ADR-0001

四者共用同一次原子替換

Goal、Work Item、Evidence 與 Gate 存在同一份 JSON snapshot，受同一個程序鎖保護。完成一件工作與解鎖其下游必須落在同一次交易內，否則讀取者會看到「A 已 DONE 但 B 仍 PENDING」的中間狀態。

指令面

指令做什麼
init / migrate在 repository root 建立 .forgepilot/；升級 state schema（備份後升級，不自動發生）
goalcreate / block / unblock / complete / cancel
work add新增 Work Item，指定 Story 與依賴
next / start純查詢下一件可執行的工作；把 READY 推進到 RUNNING
verify [--snapshot]對乾淨 HEAD，或 immutable working-tree snapshot，在隔離 worktree 跑 make verify，記錄 Evidence
gateopen / resolve / cancel——提出、決定或撤銷一個需要人判斷的問題
reviewapprove / reject；approve 在條件成立時完成工作並解鎖下游
status整份佇列，包含未解除的 Gate 數、最新 Evidence 與未完成的原因
刻意不做

Web UI、雲端服務、資料庫、daemon、multi-agent scheduler、Agent spawning、plugin framework、network API、自動 merge 或 release。以及任何能直接寫入 DONE 的路徑。

Go 1.25.5，只用標準函式庫。初始支援平台是 macOS 的本機檔案系統——程序鎖使用 OS flock，其他平台尚未驗證行為相同，因此不宣稱支援。
