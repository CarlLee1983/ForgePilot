ForgePilot · Passive DAG Ledger

它不寫程式，也不跑迴圈。
它決定什麼可以開始、什麼算完成。

一個只用 Go 標準函式庫的本機 CLI。工單拆分完成後，外部 Agent 依它的建議把一張 DAG 上的工作全部做完；它保存每一步的證據，並擋住不該推進的工作。

問題

Agent 輔助的工程有一個特定的失效模式：狀態活在對話裡。哪件事可以開始、哪件事在等誰的判斷、某次「測試通過了」是在哪一版通過的——這些都留在某次 session 的上下文中，換一個 session 就沒了。

後果不是效率問題，是可信度問題。Agent 面對規格歧義時最容易做的事，是自己選一個然後繼續往下寫；而「跑過測試了」如果沒有綁定確切的 Candidate，它就只是一句話。

ForgePilot 的位置

它不啟動 Agent、不產生 Story、不拆單、不用 LLM 判斷 PASS、不決定架構、不 merge 也不 release。迴圈由外部 Agent 跑；工程要求由經人核准的 Warrant Story 定義，正確性由 repository 自己的 make verify 判斷，該由人決定的事由人決定。ForgePilot 只負責判定下一個合法動作、把事實記下來，並擋住不該推進的工作。

核心概念

Goal Plan

工單拆分後交給 ForgePilot 匯入的一份 JSON：一個 Goal、它的節點、每個節點參照的 Story 與節點間依賴。goal import 一次建立整張 DAG；ForgePilot 只保證它是合法 DAG、Story 路徑存在，拆得對不對是上游與人的責任。

不是可隨意改寫的工作清單：再次匯入只能新增節點。

Goal

由一份 Goal Plan 建立、跨多件工作推進的目標。有 ACTIVE / COMPLETED / CANCELLED 三個狀態；最後一件工作 DONE 時自動 COMPLETED，放棄則用 goal cancel。

Work Item

Goal Plan 中的一個節點，以節點 ID 識別，參照一份 Warrant Story，有自己的狀態與依賴。它只保存 story_ref，不複製 Story 的需求。PENDING／READY 是讀取時依依賴計算的，不保存。

不是另一種獨立的 Task 物件，也不是 Story 的副本。

Gate

依附於單一 Work Item、需要明確人為決定才能解除的關卡。提出時必須列出至少兩個選項。未解除的 Gate 擋住那件工作推進，但不改變它的狀態。

不是驗證失敗，也不是逾時就自動同意。

Candidate

Verification 所針對的 immutable code identity：已 commit 的 HEAD，或用 --snapshot 從未 commit 工作樹固定下來的 snapshot。不需要 WIP commit，也不改動你的 branch 與 index。

不是branch、工作樹本身，也不是 Work Item 的狀態。

Evidence

綁定一件工作與一個確切 Candidate 的紀錄，只新增不修改。Verification（PASS / FAIL / INTERRUPTED）一定有；Human Review（APPROVED / REJECTED）只在 Goal 要求 Approval 時出現，兩者共用同一條時間軸。

不是完成宣告，也不是 Agent 的自評。

完成是條件的結果，不是一個指令

產品裡沒有 done，沒有 complete <work-id>，也沒有測試專用的捷徑。DONE 只會是 verify 在確切 Candidate 上 PASS 的結果，並與解鎖下游落在同一次交易內：

forgepilot verify schema
  ├─ 在隔離的 detached worktree，對確切的 Candidate 跑 make verify
  ├─ 記錄 Evidence                ← 一定會發生：PASS / FAIL / INTERRUPTED
  └─ 依結果與 Goal 決定狀態
       ├─ PASS，Goal 不要求 Approval、無未解 Gate ─▶ DONE，下游立刻 READY（同一次交易）
       │                                              最後一件 DONE ─▶ Goal 自動 COMPLETED
       ├─ PASS，Goal 要求 Approval ─▶ REVIEW，等人 review approve 才 DONE（approve 再檢查 Gate）
       ├─ PASS，但 Goal 非 ACTIVE，或不要求 Approval 而有未解 Gate ─▶ 留在 RUNNING
       ├─ FAIL        ─▶ 退回 RUNNING，next 給 REPAIR
       └─ INTERRUPTED ─▶ 退回 RUNNING，next 給 RESUME
          （回收前還卡在 VERIFYING 的孤兒執行，next 給 RECOVER）

沒有完成指令，所以 status 是使用者唯一能得知「為什麼還沒完成」的地方：它對每件未完成工作都說明為何不能前進（依賴、Gate、等待 approval、佔位、Goal 已結束），不能對未完成的原因沉默——這條被測試釘住。

外部 Agent 的迴圈

1

匯入一份 Goal Plan

forgepilot goal import plans/x.json 一次建立 Goal 與整張 DAG。計畫有任何一處錯，整份都不寫入。補單時改計畫檔再匯入，只能新增節點。

2

問 next，只給一個動作

next 是純查詢：START、RESUME、REPAIR、RECOVER、REVERIFY、WAIT 之一，附理由。同一 workspace 同時最多一件 RUNNING 或 VERIFYING，所以不會同時推薦兩件工作。

3

start、實作、verify

Agent 讀 Story 實作，verify 在隔離 worktree 對確切 Candidate 跑受管理專案的 make verify。PASS 即 DONE（要求 Approval 的 Goal 則進 REVIEW）。FAIL 時讀 log 修復再 verify。

4

需要人判斷時開 Gate 並停下

架構取捨、範圍變更、規格歧義——Agent 不自己選一個繼續，而是 gate open 擋住該工作。換 session 的 Agent 由 next / status 得知正在等人。

5

回到 2，直到 Goal COMPLETED

每一輪都重新問 next，不自己維護清單。最後一件 DONE 時 Goal 自動完成，next 回報 GOAL_ALREADY_COMPLETED，迴圈結束。

幾個關鍵決定

ADR-0040

驅動者在外部，ForgePilot 是被動的帳本

Claude Code 之類的 Agent 已是合格的迴圈執行者；ForgePilot 不可取代的是合法動作判定與不可偽造的完成條件。它不啟動 coding CLI、不管理安裝版本，除了 Git 與 make verify 之外不啟動任何程序。

ADR-0007

阻擋不佔用狀態欄

沒有 WAITING_HUMAN，Work Item 也沒有 BLOCKED。狀態描述工作在生命週期的位置，Gate 是另一個維度的條件。兩處各表達一次同一事實，就會需要「記住進入阻擋前是什麼狀態」這種只為修補覆寫而存在的欄位。

ADR-0006

DONE 是終態，沒有 reopen

它記錄的是已經發生的事，後續 commit 不使其失效。需要重做就在計畫檔新增一個節點，讓「為什麼重做」有地方被記錄。也因此 DONE 的工作不標示 stale——那個提示對它不對應任何行動。

ADR-0005

身分是自述的，不做認證

決策者預設取自 git config user.email，並在每一處輸出明確標示為聲明。半套的認證比不做更危險——它會讓人以為那個名字有保證。

ADR-0009

回收先於拒絕

verify 先無條件把上次被中斷的執行記為 INTERRUPTED，再判斷能不能開始新的一次。中斷是已經發生的事實，不該被任何阻擋條件扣住；能不能再跑一次，才是阻擋條件要回答的問題。

ADR-0010

完全離線

不自行 HTTP，也不 spawn gh。這個工具在沒有網路、沒有 token、GitHub 掛掉時照樣可用，而 Evidence 的結果集合不必為「遠端不可用」再開一個值。

ADR-0001

四者共用同一次原子替換

Goal、Work Item、Evidence 與 Gate 存在同一份 JSON snapshot，受同一個程序鎖保護。完成一件工作與解鎖其下游必須落在同一次交易內，否則讀取者會看到「A 已 DONE 但 B 仍 PENDING」的中間狀態。

指令面

指令做什麼
init在 repository root 建立 .forgepilot/
goal import / goal cancel由 Goal Plan 一次建立 Goal 與整張 DAG（重新匯入只能新增節點）；放棄一個 Goal
next [--json] / start純查詢唯一的下一個合法動作；把 READY 推進到 RUNNING
verify [--snapshot]對乾淨 HEAD，或 immutable working-tree snapshot，在隔離 worktree 跑 make verify，記錄 Evidence；PASS 即 DONE
gateopen / resolve / cancel——提出、決定或撤銷一個需要人判斷的問題
reviewapprove / reject；僅適用要求 Approval 的 Goal
status每個 Goal 的節點、最新 Evidence、未解除的 Gate 與每件未完成工作為何不能前進
刻意不做

Web UI、雲端服務、資料庫、daemon、啟動 coding agent 的 Runner、平行執行、plugin framework、network API、自動 merge 或 release，以及任何能直接寫入 DONE 的路徑。

Go 1.25.5，只用標準函式庫。初始支援平台是 macOS 的本機檔案系統——程序鎖使用 OS flock，其他平台尚未驗證行為相同，因此不宣稱支援。
